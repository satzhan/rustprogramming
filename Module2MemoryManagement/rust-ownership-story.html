The Life of a Value

Rust ownership, told as a story, with the real names written in the margin

The textbook version of ownership fits on an index card. Every value has an owner. There's only one owner at a time. When the owner goes away, the value goes away.

All true. It's also about as useful as saying chess is "move pieces until the other king is stuck." You can memorize that in ten seconds and still have no idea why your bishop won't go where you want it to. The interesting part of ownership is what happens when that little rule runs into the rest of the language, and it runs into almost everything.

So here's a way to hold it in your head. Picture every owner as a character in a story. Characters carry items. They hand items to each other, lend them out, pry pieces off them, and sooner or later they leave the story. Whatever they were carrying leaves with them.

There's one more person in this story, and you never see them on stage: the editor. Before anything is performed, the editor reads the entire script and sends it back covered in red pencil if anybody does something the world doesn't allow. The editor is the Rust compiler. Nearly every rule in this guide is checked on paper, before your program runs a single line. Where that's not the case, I'll point it out, because it matters.

The narrow column on the right (or the line above each paragraph, if you're on a phone) gives you the actual Rust names for whatever the story is talking about. Read the story, glance over, try the code. Every example here was compiled, and the red-pencil notes carry the real error codes you'll see from rustc.

1Who gets to be a character

The obvious characters have names. Write let sword = String::from("steel"); and someone named sword walks on stage holding something. That's the character every tutorial talks about, and it's the reason people think the story ends there. It doesn't.

let bindingthe owner

Items can hold other items. A backpack has pockets, and the pockets have stuff in them. A struct owns its fields. A tuple owns its elements. An array owns every one of its slots. So ownership isn't really a list of characters and their belongings. It's a tree, like a set of nesting dolls: a character at the root, items under them, items under those.

Hang on to that picture. Most of the rules later on come down to one question: which branch of the tree are you touching?

struct fieldstuple elementsarray elementsthe ownership tree

Some items are bigger on the inside. A String sitting in your variable is small. It's really just three numbers: where the text is, how long it is, and how much room has been reserved. The text itself lives somewhere else, out on the heap.

Think of a coat check. The ticket is in your pocket and the coat is in the back room. You own the ticket, and the ticket is responsible for the coat. That's still one owner, not two. It's one owner holding a thing that knows where the coat is.

String, Vec<T>, Box<T>stack part: pointer, length, capacityheap buffer

Then there are the extras, the people with no names who walk on for one line. In make_title().len(), the String that make_title hands back never gets a name. It exists long enough for .len() to look at it, and at the semicolon it walks off, item and all.

temporariesdropped at the end of the statement

A closure can be a character too. If you write move || ..., you're hiring a companion and handing them your gear outright. From then on it's theirs.

closuresmove |..| { .. }capture by value

And some things aren't carried by anyone. They're landmarks, part of the world itself, like a mountain on the map. The text of "hello" is baked right into your program file. Nobody owns it and it never leaves, which is why you can point at it for as long as you like.

A small correction to something you may have read earlier in this course: string literals don't live on the stack. The little reference you hold can sit on the stack, but the bytes it points at are in the program's read-only data.

staticstring literals: &'static strlives for the whole program

2Handing things over

Here's the scene everybody meets first.

fn main() {
    let scroll = String::from("map to the treasure");
    let hero = scroll;          // scroll hands it over
    println!("{}", scroll);    // scroll speaks about it anyway
    println!("{}", hero);
}

Editor: error[E0382]: borrow of moved value: scroll

The item went from one character to another, and the first one's hands are empty. Passing a value into a function does the same thing. So does returning one.

movelet b = a;passing argumentsreturnE0382 use of moved value

So what physically happened on that second line? Less than you'd guess. The three numbers of the coat-check ticket got copied into hero's spot, and that's all. Nobody went back to scroll's spot to wipe it. The coat didn't move either.

The whole "transfer" is paperwork. It's like changing the name on the deed to a house: the house stays put, and the editor simply crosses out the old name and won't let it speak about the house again. One consequence surprised me the first time I saw it. Moving a String with a million characters costs exactly as much as moving one with a single character.

a move is a bitwise copy of the stack partplus the source being marked invalid at compile time

Empty hands aren't a permanent condition. If the binding was declared mut, you can give it something new and it's a proper character again.

let mut bag = String::from("rope");
let given = bag;                 // bag is empty-handed now
bag = String::from("lantern");   // and now it isn't
println!("{} {}", bag, given);   // lantern rope
reassigning a moved-from variablereinitialization

Loops trip people up. Imagine a character walking laps, handing out an amulet on each lap. On lap one, fine. On lap two, what's in their hand? Nothing.

fn take(_s: String) {}

fn main() {
    let gift = String::from("amulet");
    for _ in 0..2 {
        take(gift);
    }
}

Editor: error[E0382]: use of moved value, value moved here, in previous iteration of loop

The fix is to restock before the next lap:

let mut gift = String::from("amulet");
for _ in 0..2 {
    take(gift);
    gift = String::from("another amulet");
}

The editor is happy, because on every lap there's something in hand to give.

moves inside loop, for, while"value moved in previous iteration"

When you call a method, look at how the method takes its receiver, because that's the method telling you what it plans to do with your item.

If it takes self, the item goes up on the altar and doesn't come back. s.into_bytes() is like trading in your car: you get something for it, but the car is gone. If it takes &self, it only wants to look. If it takes &mut self, it wants to tinker, and you get the item back afterwards, possibly changed.

fn m(self) consumesfn m(&self) readsfn m(&mut self) modifiese.g. String::into_bytes

A for loop over a collection is a handover too, which is easy to miss because there's no let in sight.

let bag = vec![String::from("rope"), String::from("torch")];
for item in bag {
    println!("{}", item);
}
println!("{}", bag.len());

Editor: error[E0382]: borrow of moved value: bag

The loop took the whole bag and unpacked it item by item. When the loop ends, there's no bag. If you only wanted to look, write for item in &bag. If you wanted to change the items in place, write for item in &mut bag.

for x in v calls IntoIterator::into_iter(v)for x in &v borrowsfor x in &mut v borrows mutably

One more thing about handing over. Whether you're allowed to change an item depends on who's holding it, not on the item. Each new holder applies for their own license.

let x = String::from("plain sword");
let y = x;
let mut z = y;                    // z has a crafting license
z.push_str(", sharpened");

Neither x nor y could have sharpened it. z can, because mut belongs to the name, not to the String.

mut is on the bindingnot part of the type

3Taking pieces off

Remember the tree. Since items hold items, you can sometimes take just one branch.

struct Knight { name: String, sword: String }

let k = Knight { name: String::from("Ada"), sword: String::from("gem blade") };
let blade = k.sword;          // pry the gem blade loose
println!("{}", k.name);       // the rest of the knight is still here

That's fine. What you can't do now is treat the knight as a whole, because a piece is missing. Write let whole = k; after that and you get error[E0382], use of partially moved value. The parts that are left still get cleaned up normally when k's scene ends.

partial movelet f = s.field;

There's an exception. Some items come with a disposal ceremony, a bit of code that runs when they're destroyed. You can't pry parts off those, for the same reason you can't return a sealed appliance after opening it up: the ceremony expects the whole thing to be there.

struct Relic { gem: String }
impl Drop for Relic { fn drop(&mut self) { } }

let r = Relic { gem: String::from("ruby") };
let g = r.gem;

Editor: error[E0509]: cannot move out of type Relic, which implements the Drop trait

impl Dropno partial moves out of itE0509

You also can't hand over something that isn't yours. If someone lent you an item, it's theirs. If you're looking at a slot in a vector, you're looking at a museum display, and museums don't let you walk out with the exhibits. If it's a landmark, it belongs to the world.

let shelf = vec![String::from("idol")];
let idol = shelf[0];

Editor: error[E0507]: cannot move out of index of Vec<String>

Why not? Think about what would happen. The vector still believes slot zero holds a string. When the vector is cleaned up, it would clean up slot zero. So would idol. That's the same coat thrown away twice.

can't move out of *rcan't move out of v[i]can't move out of a staticE0507, E0508

So how do you get it out? You do the adventure-movie trick with the golden idol: put something on the pedestal as you lift the treasure off, so the slot is never empty.

let mut shelf = vec![String::from("idol")];
let idol = std::mem::take(&mut shelf[0]);
// got "idol", shelf now [""]

take puts down the type's default value, an empty string here. replace lets you pick the substitute yourself. For an Option, .take() leaves None behind.

std::mem::takestd::mem::replacestd::mem::swapOption::taketake uses Default

Patterns grab. When you write let (name, _) = pair; or a match arm that binds a String field by value, that field gets handed to the new name. If you only wanted to look, match on a reference instead, and the bindings become references for you:

let pair = (String::from("map"), 7);
match &pair {
    (name, n) => println!("{} {}", name, n),  // name is a &String
}
let (name, _) = pair;                        // this one really takes it

The older way to say "just look" inside a pattern is the ref keyword. You'll still see it in plenty of code.

destructuring moves by defaultref, ref mutmatch ergonomics / default binding modes

4Leaving the story

To watch characters leave, it helps to have items that announce their own departure. Here's one. We'll use it for the rest of the chapter.

struct Loud(&'static str);

impl Drop for Loud {
    fn drop(&mut self) {
        println!("{} leaves", self.0);
    }
}

When a character's scene ends, meaning the closing } of the block where they were declared, their items dissolve. That's the moment memory gets freed. It works like a hotel checkout that clears the room automatically: you don't call housekeeping, you just leave.

the Drop traitruns at end of scopethis pattern is called RAII

Now, who leaves first? Try to predict it before you open the answer.

struct Pack { first: Loud, second: Loud }

fn main() {
    let _veteran  = Loud("veteran");
    let _newcomer = Loud("newcomer");
    let _pack = Pack { first: Loud("pocket one"),
                       second: Loud("pocket two") };
    println!("the scene ends");
}
Guess the output, then open

pocket one leaves
pocket two leaves
newcomer leaves
veteran leaves

Two different orders are at work. Characters leave in reverse order of arrival, like a stack of plates. That's deliberate: a newcomer might depend on the veteran who was there first, so the newcomer has to go before the veteran does. Inside a pack, though, the pockets empty in the order they were written down. The pack arrived last, so it left first, and its pockets went one, two.

The same picture explains why dissolving is recursive. When a Vec<String> goes, every String in it goes, and every buffer those strings pointed at goes too. The whole branch of the tree comes down.

drop orderlocals: reverse declaration orderfields and elements: declaration orderdrop glue (recursive)

You might expect some special "destroy this now" command. There isn't one, really. std::mem::drop is defined, in the actual standard library, like this:

pub fn drop<T>(_x: T) {}

That's the whole function. You hand your item to a character whose scene is one line long. They leave, and the item leaves with them. Ending the owner is the destruction. (You're not allowed to call the .drop() method yourself, by the way. The editor would catch you running the ceremony twice.)

std::mem::drop(x)an ordinary movecalling x.drop() directly is E0040

Here's the first place the editor can't settle everything on paper.

let coin = std::env::args().count() > 1;
let amulet = Loud("amulet");
if coin { drop(amulet); }
println!("the scene ends");

Did the amulet get handed away or not? It depends on something that only happens when the program runs. So the compiler quietly leaves a note for the narrator, a hidden flag saying "was it given away?" At the end of the scene the flag gets checked, and the item dissolves only if it's still here. Run it with no arguments and you'll see "the scene ends" first, then "amulet leaves." Pass any argument and the order flips.

drop flagsa real runtime check

Extras can get promoted. Normally a temporary leaves at the semicolon, but if you immediately take a reference to it and give that reference a name, Rust keeps the extra around for as long as the name needs it.

let r = &Loud("promoted extra");
println!("still here: {}", r.0);
// "promoted extra leaves" prints at the end of the scene

The exact rules for how long temporaries live were adjusted in the 2024 edition, mostly for temporaries in the last expression of a block and in if let. If you ever see a surprising drop time, check which edition your project uses.

temporary lifetime extensionlet r = &make();

Pointing isn't grabbing. Here's a puzzle that catches experienced people.

let keeper = Loud("keeper");
let _ = keeper;
let _ = Loud("extra");
let _named = Loud("named extra");
println!("the scene ends");
Guess the output, then open 
extra leaves
the scene ends
named extra leaves
keeper leaves

The lone underscore means "don't bind anything." So let _ = keeper; just points at the keeper and says "that one," and the keeper keeps its item. let _ = Loud("extra"); points at an extra who has no name, and nobody takes the item, so the extra leaves at the semicolon. _named starts with an underscore but it's a real name. It takes the item and lives to the end of the scene.

let _ = x; does not movelet _y = x; does

Now something that surprises people who think Rust promises "no memory leaks." It doesn't promise that. What it promises is that nothing dissolves twice and nothing is used after it's gone. An item disappearing without its ceremony is allowed, and there are several ways to do it on purpose or by accident:

std::mem::forget throws an item into the void. Box::leak turns an item into a permanent landmark and gives you a &'static mut to it. And two guilds that each hold the other's charter never disband, like two people each waiting for the other to hang up the phone. That's a reference cycle with Rc, and chapter 8 comes back to it.

5Copying instead of handing over

Why doesn't this fail the way the scroll did?

let a: i32 = 5;
let b = a;
println!("{} {}", a, b);   // 5 5

Because an integer isn't an object you carry around. It's more like a fact. If I tell you a phone number, I don't forget it. We both have it now, completely independently. Types that behave this way are marked Copy: the integers, floats, bool, char, shared references, and tuples and arrays made only of those.

the Copy traitimplicit bitwise duplicatesource stays valid

Could a String be Copy? Think about what the copy would be: a second coat-check ticket for the same coat. Now both tickets get turned in at the end of the night, and the coat gets thrown away twice. That's the whole reason a type can't be both Copy and have a Drop ceremony. The compiler simply won't let you declare both.

Copy and Drop are mutually exclusiveotherwise: double free

If you really do want two coats, you commission a tailor. .clone() makes a genuine second item with its own heap memory. It's explicit on purpose, because it can cost real time and memory, and Rust wants you to see that cost written in your code.

.clone()the Clone traitdeep copy, usually allocates

References follow the same logic. A visitor's pass to a museum can be photocopied as much as you like, since a hundred people looking doesn't hurt anything. A work order to repair one particular blade can't be photocopied, because two smiths hammering the same blade at the same time is a mess. So &T is Copy and &mut T isn't.

&T is Copy&mut T is nottwo &mut at once = a data race

6Lending

Handing things over all the time would be exhausting, so characters also lend. The borrower gets to use the item, and the owner keeps it. But lending comes with conditions, and every one of them exists to protect the owner's item.

First condition: no loan can outlive the lender. When the lender's scene ends, their items dissolve, so a loan still floating around afterwards would be pointing at nothing. It's like a library that's closing for good: every book has to be back before the doors lock.

let loan;
{
    let lender = String::from("lantern");
    loan = &lender;
}                           // lender's scene ends here
println!("{}", loan);       // ...but the loan is used here

Editor: error[E0597]: lender does not live long enough

borrowing: &xlifetimesE0597

Second condition: while an item is lent out for viewing, it's frozen. The owner still owns it, but can't give it away, destroy it, or change it.

let mut shield = String::from("shield");
let look = &shield;
shield.push('!');          // changing it while someone is looking
println!("{}", look);

Editor: error[E0502]: cannot borrow shield as mutable because it is also borrowed as immutable

Now swap the last two lines:

let mut shield = String::from("shield");
let look = &shield;
println!("{}", look);       // last time look is used
shield.push('!');           // fine

That compiles. The loan doesn't last until the end of the block. It lasts until the borrower last uses it, and the owner gets full rights back right after. For years Rust didn't work this way and the old behavior was a constant annoyance, so if you read older blog posts complaining about this, that's why.

shared borrow &T freezes the ownerE0502NLL: non-lexical lifetimesexception: interior mutability, chapter 8

Third condition: while the item is out for repair, the owner can't even look at it. Your car is in the shop; you don't get to sit in it.

let mut shield = String::from("shield");
let fix = &mut shield;
println!("{}", shield);     // peeking during the repair
fix.push('!');

Editor: error[E0502]: cannot borrow shield as immutable because it is also borrowed as mutable

Why so strict? Because a repair might change the item in a way that makes whatever you were looking at meaningless. The last example in this chapter shows exactly that.

mutable borrow &mut Texclusive: no other access at allaliasing XOR mutation

A character leaving the stage can't hand you a note that points at their own belongings. Those belongings are about to dissolve.

fn note(_s: &String) -> &str {
    let local = String::from("my own belongings");
    &local
}

Editor: error[E0515]: cannot return reference to local variable local

A returned reference has to point at something that will still exist after the function ends. In practice that means something the caller lent in, or a landmark.

returning &Tmust come from an input or be 'staticE0515

If a struct holds a reference, it's holding a map to somebody else's stash. The map has to say whose stash, so the editor can check the map never outlives the stash.

struct Map<'a> { stash: &'a str }

let treasure = String::from("under the old oak");
let m = Map { stash: &treasure };

That 'a doesn't do anything at runtime. It's a label, a way of writing "this map depends on whoever owns the treasure" into the type.

lifetime parametersstruct S<'a> { r: &'a T }

Back to the tree. Since fields are separate branches, you can lend the shield to one person and the sword to another, both for repair, at the same time.

struct Kit { shield: String, sword: String }

let a = &mut kit.shield;
let b = &mut kit.sword;      // fine, different branches
a.push('!');
b.push('!');

But try getting the sword through a method:

impl Kit {
    fn sword_mut(&mut self) -> &mut String { &mut self.sword }
}

let a = &mut kit.shield;
let b = kit.sword_mut();
a.push('!');

Editor: error[E0499]: cannot borrow kit as mutable more than once at a time

This one feels unfair at first. You know the method only touches the sword. But the editor doesn't read the method's body when checking your call. It reads the signature, and the signature says &mut self: "lend me the whole kit." The signature is a promise, and the editor holds you to exactly what it says.

disjoint field borrowsborrow checking is per functionsignatures are the contractE0499

Here's the concrete example I promised. You can't make a bag bigger while someone is counting what's inside.

let mut bag = vec![1, 2, 3];
for x in &bag {
    if *x == 2 { bag.push(4); }
}

Editor: error[E0502]: cannot borrow bag as mutable because it is also borrowed as immutable

This isn't the editor being fussy. When a vector runs out of room, push moves everything to a bigger room somewhere else on the heap and frees the old one. The loop would keep counting in the old room, which is now empty and possibly handed to someone else. In C++ this is a real bug that ships in real programs. Here, it's a red mark on the script.

iterator invalidationreallocation on push

7Originals and windows

Once you have both owning and lending, a pattern shows up all over the standard library: the same kind of data comes in two forms, the original and a window onto someone's original. A house and a photo of the house.

String is a scroll you own, &str is a window onto some text. Vec<T> is a shelf you own, &[T] is a window onto a row of items. Same with PathBuf and &Path, and Box<T> and &T. A good habit: take windows as function parameters when you only need to read. A &String turns into a &str automatically, so taking &str lets callers pass either.

String / &strVec<T> / &[T]PathBuf / &PathBox<T> / &Tderef coercion

To go from window to original, you transcribe: look through the window and write out your own scroll. That's .to_owned() or .to_string(), and it allocates new memory, so it isn't free.

.to_owned().to_string()the ToOwned trait

Sometimes you don't know in advance whether you'll need your own copy. A library book is a good model: you read it for free, and only if you want to write in the margins do you go buy your own.

use std::borrow::Cow;

fn tidy(s: &str) -> Cow<str> {
    if s.contains(' ') {
        Cow::Owned(s.replace(' ', "_"))   // had to buy a copy
    } else {
        Cow::Borrowed(s)                  // just the library copy
    }
}

tidy("clean") costs nothing. tidy("needs work") allocates, because it had to change something.

Cow<'a, T>clone-on-write

8Changing the rules of possession

"One owner" is a strong rule, and sometimes the thing you're modeling really does have many owners. A node in a graph that several other nodes point to, say. For that, Rust has guild property. It works like a timeshare: many members each hold a token, and the property only goes away when the last member gives up their token.

use std::rc::Rc;

let hall = Rc::new(String::from("guildhall"));
let member = Rc::clone(&hall);
println!("members: {}", Rc::strong_count(&hall));   // 2

Rc::clone doesn't copy the hall. It hands out another token and bumps the member count.

Rc<T> single-threadedArc<T> thread-safeRc::cloneRc::strong_countreference counting

What about the two guilds from chapter 4 that each held the other's charter? The fix is to let one side merely know the other's address, without being a member. Knowing where the guildhall is doesn't keep it open.

let address = Rc::downgrade(&hall);
drop(hall);
drop(member);
println!("still standing? {}", address.upgrade().is_some());
Guess what prints, then open

still standing? false. The last two members left, so the hall dissolved. The address still exists, but upgrade() checks and finds nothing there, so it returns None. That check is how a Weak stays safe.

Weak<T>Rc::downgrade.upgrade() returns Optionbreaks reference cycles

Guild property has a catch. With many members, nobody has exclusive rights, so an Rc only gives you &T: look, don't touch. The one exception is when you happen to be the only member left. Then Rc::get_mut hands you a &mut, and Rc::make_mut will even make you a private copy first if others are still around.

Rc derefs to &T onlyRc::get_mutRc::make_mut

So how do you get shared ownership and change things? You station a referee on stage. Up to now, every rule was checked by the editor before the show. These types move the check into the performance itself.

A RefCell keeps a sign-out sheet. Every time someone borrows, it writes that down, and it refuses a repair while anyone is still signed out for viewing. Refuses loudly:

use std::cell::RefCell;

let ledger = RefCell::new(String::from("sword"));
let looking = ledger.borrow();
let fixing = ledger.borrow_mut();    // compiles fine...
thread 'main' panicked at ...
already borrowed: BorrowMutError

Notice what happened. It compiled. The rule is exactly the same one the editor enforces in chapter 6, but now it's caught during the run, and breaking it crashes the program instead of failing the build.

interior mutabilityRefCell<T>.borrow(), .borrow_mut()panics with BorrowMutErrora real runtime check

A Mutex is a steward holding the only key, like the key to a single-person restroom. If someone else has it, you wait. .lock() is asking for the key, and when the guard it returns goes out of scope, the key goes back on the hook.

A Cell is cleverer and cheaper. It never lends the item at all. You can only swap a whole item in or copy one out, with .set() and .get(). Since nobody ever holds a reference to the inside, there's nothing to keep track of, so no sign-out sheet is needed.

Underneath all of these sits one primitive, UnsafeCell. It's the only legal way in Rust to change something through a &.

Mutex<T>, .lock()RwLock<T>Cell<T>, .get(), .set()UnsafeCell<T>OnceCell, atomics

Last, an odd one. Remember that a move copies bytes to a new place. For almost everything, that's harmless. But picture a shrine whose inscriptions give directions measured from the shrine itself: "the key is three paces north of here." Move the shrine and the inscriptions are lies. Some data is like that, it contains pointers into itself, and Rust's async code produces it all the time.

Pin nails such an item to the floor, promising it will never move again. Most types don't care where they are, and those are marked Unpin; for them, pinning is a formality and they can still be moved.

Pin<P>Unpin / !Unpinself-referential data, async futures

9Companions and parallel storylines

A closure decides for itself how to hold what it uses. It picks the lightest grip that works: just look if looking is enough, borrow for repair if it changes something, carry it only if it has to. Writing move forces it to carry everything.

Separately, the closure's body decides how many times it can be called. If the body gives away something it's carrying, it can only do that once. It's a companion with a single-use potion.

let potion = String::from("potion");
let drink = move || { let p = potion; println!("drank {}", p); };
drink();
drink();

Editor: error[E0382]: use of moved value: drink

The first call consumed the closure itself. A closure that only tinkers with its gear can be called many times (FnMut), and one that only looks can be called anywhere, anytime (Fn).

capture modes: &, &mut, by valuemoveFnOnce, FnMut, Fnedition 2021: captures individual fields

Threads are storylines running side by side. Now there's a new question: which items are allowed to cross from one storyline to another?

use std::rc::Rc;
use std::thread;

let token = Rc::new(5);
thread::spawn(move || println!("{}", token));

Editor: error[E0277]: Rc<i32> cannot be sent between threads safely

An Rc's member count is kept in pencil with nobody guarding it. If two storylines both added or removed a member at the same moment, the count could come out wrong, and a wrong count means dissolving too early or never. Arc keeps its count with atomic operations, which are safe to update from several threads at once, so Arc may cross.

There's a second marker for items that may be looked at from several storylines at once. A RefCell can be handed to another thread, but not shared between two, because its sign-out sheet isn't guarded either.

A spawned thread is an expedition of unknown length. You don't know when it comes back, so it can't borrow anything from camp: camp might be packed up before it returns.

let supplies = vec![1, 2, 3];
let h = thread::spawn(|| println!("{:?}", supplies));

Editor: error[E0373]: closure may outlive the current function, but it borrows supplies

That's why you see move on nearly every thread::spawn. The party carries its own supplies.

If you can promise every expedition returns before camp breaks, borrowing is fine again:

thread::scope(|s| {
    s.spawn(|| println!("scout sees {:?}", supplies));
    s.spawn(|| println!("cook sees {:?}", supplies));
});                                  // both are back by here
println!("camp still has {:?}", supplies);

To share one changeable thing among many storylines, put the two ideas from chapter 8 together: guild property that's safe across threads, holding a steward with a key.

use std::sync::{Arc, Mutex};

let chest = Arc::new(Mutex::new(0));
for _ in 0..4 {
    let chest = Arc::clone(&chest);
    crew.push(thread::spawn(move || {
        *chest.lock().unwrap() += 1;
    }));
}

Each thread gets its own membership token, and they take turns with the key. You'll write this shape many times.

Finally, couriers. Sending a value down a channel is like mailing a package: once it's in the mailbox, it's not in your hands.

let (tx, rx) = std::sync::mpsc::channel();
let parcel = String::from("letter");
tx.send(parcel).unwrap();
println!("{}", parcel);

Editor: error[E0382]: borrow of moved value: parcel

That's the same error as the very first scroll example. Nothing new is going on. send takes its argument by value, and that's the whole trick: ownership is how Rust knows only one thread can touch the letter at a time.

10Dark magic

Inside an unsafe block you're allowed to do a few things the editor can't verify. It doesn't switch the editor off. Ordinary references are still checked exactly as before. It just gives you some extra spells, and you vouch for them.

std::ptr::read is a forgery spell. It copies an item's bytes into a new character without crossing out the original. Now two characters believe the item is theirs, and when both scenes end, the ceremony runs twice. That's a double free, which is exactly the kind of bug the whole ownership system exists to prevent.

unsafe { }std::ptr::readraw pointers *const T, *mut Trisk: double drop

So there are also spells for doing the bookkeeping yourself. ManuallyDrop lifts the automatic dissolving: the item stays when the scene ends, and it's your job to dispose of it (or to leak it on purpose). MaybeUninit is a reserved seat. The seat exists, nobody is in it yet, and you promise to fill it before anyone checks who's sitting there.

One honest caveat. The exact rules that unsafe code must follow about aliasing aren't officially finished. There are candidate models, called Stacked Borrows and Tree Borrows, and a tool named Miri that checks your code against them, but neither is the final word yet.

Where the story breaks down

Every analogy is wrong somewhere, and it's worth knowing where, so you don't lean on it in the wrong place.

A move is not a character physically carrying the whole item across the stage. Only the small part, the coat-check ticket, gets copied. The coat stays in the back room. That's the reason moving a huge vector is cheap, and the story doesn't show it unless you remember the coat check.

The editor isn't the only enforcer. Three things in this guide happen while the program runs: drop flags (chapter 4), RefCell's sign-out sheet, which panics, and Mutex's key, which makes threads wait (chapter 8). Everything else is settled before the program starts.

And the editor is cautious, not perfect. It rejects some programs that would actually have been safe. The best-known case is returning a borrow conditionally from inside a loop. A newer borrow checker, called Polonius, is being built to accept more of those. I don't know its current status; check the Rust blog if it matters to you. When the editor rejects something you're sure is fine, it's worth asking two questions: is there really no way this could go wrong, and if not, can I restructure so the editor can see that too?
