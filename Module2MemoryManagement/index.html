Week 2 · Memory Management · A Hands-On Lab

Every value has exactly one owner.
Everything else follows.

C trusts you to free memory. Java hires a janitor to do it at runtime. Rust does something stranger: it proves at compile time that memory is freed exactly once, at exactly the right moment. This lab lets you push the buttons and watch it happen.

Rule 1 — every value has an owner
Rule 2 — only one owner at a time
Rule 3 — owner leaves scope ⇒ value is dropped

ENTRY 01

The problem nobody escapes

from: 01-intro, 03-approaches

Every program needs memory; the only question is who returns it, and when. Get the timing wrong and you don't get a polite error — you get one of these three classics. Rust's entire ownership system exists to make all three impossible to compile.

use-after-free

You return a book to the library, then keep reading it on the bus. Someone else has checked it out — now you're both scribbling in the same margins.

memory freed, then read

double free

You return the same book twice. The librarian's records are now corrupted, and the next person's checkout is built on lies.

memory freed twice

memory leak

You never return the book at all. One book is fine. A long-running server "borrowing" books for six months empties the library.

memory never freed
Hold this question while you scroll: could a compiler catch these bugs before the program ever runs? C says no. Java dodges the question. Rust's answer is the rest of this page.

ENTRY 04
Be the borrow checker
from: 05-borrowing

    
Moving ownership everywhere would be exhausting, so Rust lets you lend a value: &x is a reading pass, &mut x is an editing pass. One law governs the whole library:

    
📜 At any moment: many readers or one writer — never both.

    
Try to break it. The verdicts below are the real error codes rustc would give you.

    

      

        

          
          
          
        

        
No borrows yet. x is free as a bird.

        
Real-world nuance: since 2018, a borrow ends at its last use, not at the closing brace. So readers that are finished quietly leave the room before a writer arrives. (This trips up older tutorials — see quiz Q3.)

      

      

        

          
let mut x = 5

          
no active borrows

        

        
Why this law? Because "two people editing one Google Doc with no sync" is a data race. Rust refuses to compile the race instead of debugging it later.

      

    

  







  

    
ENTRY 05
ref: borrowing inside a pattern
from: 06-ref-keyword

    

      

        
match normally moves non-Copy values into its arms. ref says "bind a reference instead" — same idea as &, but written on the pattern side of the = instead of the value side.

        
let name = String::from("Alice");match name {    ref n => println!("{n}"), // borrows}println!("{name}"); // still alive ✓

      

      

        
Honest footnote: modern Rust's "match ergonomics" (2018+) auto-borrow when you match on &name, so day-to-day code rarely writes ref anymore. Teach it as a decoder ring for older code and a precision tool — not a daily driver.

        
Mental hook: & creates a reference to a value; ref requests a reference from a pattern. Same coat-check ticket, issued at a different window.

      

    

  







  

    
ENTRY 06
Zoom out: where does the heap even come from?
from: 01-intro, 02-virtual-memory

    
Everything above happened inside one process's address space — a polite fiction maintained by the OS. Your program sees a vast private street of addresses; the OS maps the few addresses you actually touch onto scarce physical RAM, one page at a time. Touch a page that isn't resident and you get a page fault: the OS pauses you, fetches the page, and resumes as if nothing happened.

    
Click virtual pages to access them. 3 physical frames, 6 virtual pages, least-recently-used eviction. Try to discover an access pattern that never faults after warm-up — then one that always faults (that pathological case is called thrashing).

Connection back to Rust: the heap is "slow" partly because allocation may wander through this machinery, and cache/page locality is why one contiguous [u8; N] frame buffer (your week 1 graphics code!) beats a tangle of pointers. Stack frames, by contrast, are almost always hot in cache — that's the performance story behind "prefer the stack."
