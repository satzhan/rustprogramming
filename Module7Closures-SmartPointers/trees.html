Trees, with keys you can copy

A tree node is a locker with two hooks. In Rust, the keys to these lockers can be copied, and every locker door carries a sign saying who is inside. This page is about holding those keys: looking at a tree, carrying numbers through it, building one, rewiring one, and knowing what every move costs the machine.

What we're working with

Every tree on this page is built from one small struct. It comes already written. You use it, you never type it:

#[derive(Debug, PartialEq, Eq)]
pub struct TreeNode {
    pub val: i32,
    pub left: Option<Rc<RefCell<TreeNode>>>,
    pub right: Option<Rc<RefCell<TreeNode>>>,
}

impl TreeNode {
    #[inline]
    pub fn new(val: i32) -> Self {
        TreeNode {
            val,
            left: None,
            right: None,
        }
    }
}

A number and two hooks, left and right. The type on those hooks is the subject of the whole page, and it's a mouthful, so read it from the inside out:

  • TreeNode is the locker itself: a number and two hooks.
  • RefCell<TreeNode> is that locker with a sign hanging on its door, saying whether anyone is inside.
  • Rc<...> is a key to it. Not the only key. This kind can be copied.
  • Option<...> means the hook might be empty.

So left reads as maybe a copyable key to a locker with a sign on its door.

If you've worked with a list built from Option<Box<ListNode>>, the difference is the copying. A Box is the one and only key to its locker. Fine for walking a list from the front, but a tree gets used in more ways than that. You'll want a line of nodes waiting their turn, a pile of nodes to come back to, a node handed back to whoever asked for it, a struct that keeps hold of nodes between calls. Each of those means someone other than the parent holds a key. Rc lets them.

And once several people hold keys to the same locker, changing what's inside needs a rule they can all check. That's the sign on the door, RefCell.

Most tasks hand you the top of a tree like this:

fn something(root: Option<Rc<RefCell<TreeNode>>>) -> ...

You own one key to the top locker. Through it you can reach everything else. Work on trees comes in four kinds:

  • Reading. Walk the tree and come back with an answer. A count, a list of values, a yes or no. Nothing changes.
  • Rearranging. Same lockers, hung in a new shape, or with some thrown away.
  • Building. Rent new lockers and hand back the key to the top one.
  • Pointing. The answer is a node that's already in the tree, so you hand back a key to it.

Four colors carry through the pictures, and through the words that name them:

a key you holda tally, the number of keys to a lockera look, someone peeking insidea working tag, someone changing things

Sections 1 and 2 are the two wrappers. After that, each section adds one way of holding the tree. Read them in order.

1

Keys you can copy

There's a hardware store down the road that cuts keys. You hand over a key, wait half a minute, walk out with two. Nobody builds you a second locker. The copy opens the same door.

Rc works like that, with one addition: a tally sheet taped inside the locker door, counting the keys. Rc stands for reference counted, and the tally is the count.

  • Rc::new(value) rents a locker. One trip to the allocator, for a block big enough to hold the value plus the tally. You get back an address: 8 bytes.
  • Rc::clone(&key) cuts a copy. No new locker, no trip to the allocator. It adds one to the tally and hands you another 8-byte address, the same one.
  • When a key goes away (its variable goes out of scope, or you call drop), the tally goes down by one. When it reaches zero, whoever held the last key empties the locker: the value inside is dropped and the memory goes back.
let a = Rc::new(String::from("seven"));
println!("{}", Rc::strong_count(&a)); // 1

let b = Rc::clone(&a);
let c = Rc::clone(&a);
println!("{}", Rc::strong_count(&a)); // 3
println!("{} {} {}", a, b, c); // seven seven seven

drop(b);
println!("{}", Rc::strong_count(&c)); // 2

Rc::strong_count reads the tally. (Strong, because there's a second kind of key that doesn't count. Section 14.) Notice a, b and c all print seven: there's only one string, and three ways to reach it.

a.clone() does the same thing as Rc::clone(&a). Both copy the key. This page writes Rc::clone when a single key gets copied, because it says what it does. Nobody reading it will wonder whether the whole string got copied.

Now with tree nodes. Hanging a key on a hook is the same as handing it to a variable. The hook holds it, the tally counts it:

let leaf = Rc::new(RefCell::new(TreeNode::new(3)));
let mut top = TreeNode::new(1);
top.left = Some(Rc::clone(&leaf));
println!("{}", Rc::strong_count(&leaf)); // 2: `leaf` and the hook

let copy = top.left.clone(); // cloning an Option<Rc<..>> copies a key
println!("{}", Rc::strong_count(&leaf)); // 3

drop(copy);
drop(top); // dropping a node drops the keys on its hooks
println!("{}", Rc::strong_count(&leaf)); // 1

Look at the middle line. top.left is an Option<Rc<...>>, and cloning an Option clones what's inside, so top.left.clone() is a key copy too. You'll write something.left.clone() constantly in tree code, and every single time it costs 8 bytes and a tick on a tally. The subtree hanging off that hook isn't touched.

The last line is the other half. Dropping top dropped the node, which dropped the keys on its hooks, which took the tally on leaf down to 1.

What the machine holds

use std::mem::size_of;
println!("{}", size_of::<Rc<RefCell<TreeNode>>>()); // 8
println!("{}", size_of::<Option<Rc<RefCell<TreeNode>>>>()); // 8
println!("{}", size_of::<TreeNode>()); // 24

factOn a 64-bit machine that prints 8, 8 and 24. An Rc is one address. Wrapping it in Option costs nothing extra, because no real Rc ever holds address zero, so Rust uses zero to mean None. An empty hook weighs exactly as much as a full one. The node is 24 bytes: two 8-byte hooks, a 4-byte number, and 4 bytes of padding so the next node in an array would line up on an 8-byte boundary.

factWe counted allocations while building one node with Rc::new(RefCell::new(TreeNode::new(1))): one allocation, 48 bytes. Rc::clone made zero. Building a seven-node tree made seven allocations, 336 bytes.

A Box tree node would be the 24 bytes on the right and nothing else. This one is twice that. Section 14 shows what the extra costs in time.

Change a node through a plain Rc, and it doesn't compile

fn main() {
    let a = Rc::new(TreeNode::new(1));
    let b = Rc::clone(&a);
    a.val = 5; // a locker with two keys: nobody gets to just change it
}

Several keys, one locker. If any key-holder could just walk in and change things, the others would find their locker rearranged with no warning, maybe in the middle of reading it. So an Rc by itself only ever lets you look. Changing what's inside takes the sign on the door.

2

The sign on the door

Picture a card hanging on every locker door. Anyone may walk up, add a tick to the card meaning "looking," and peek inside. Five people can look at once, ten, a hundred. To change something you hang the working tag instead, and you may only do that when the card has no ticks at all. Done? Rub out your tick, or take your tag down.

Shared and mutable references follow the same rule: many readers, or one writer. With & and &mut, the compiler checks the rule before the program ever runs. A RefCell checks it while the program runs, every time a door opens. A guard stands at the door and reads the card.

  • .borrow() adds a tick and hands you a guard, a Ref. Through it you read the node as if you held a &TreeNode.
  • .borrow_mut() hangs the working tag and hands you a RefMut, which works like a &mut TreeNode.
  • When the guard goes away, so does its tick or tag.
let node = RefCell::new(TreeNode::new(1));

node.borrow_mut().val += 10; // working tag, taken down at the `;`
let v = node.borrow().val; // looking tick, erased at the `;`
println!("{}", v); // 11

{
    let a = node.borrow();
    let b = node.borrow(); // two lookers at once: fine
    println!("{} {}", a.val, b.val); // 11 11
} // both ticks erased here

let mut w = node.borrow_mut(); // nobody is looking now
w.val = 0;

When does a guard go away? If you never put it in a variable, at the end of its statement, the ;. If it's in a let, at the end of the enclosing block, or when you drop it.

factThe card is one number inside the RefCell, 8 bytes on this machine. It's 0 when the door is free, the number of lookers while people look, and -1 while someone works. We read it straight out of memory around a few guards: 0, then 1, then 2, back to 0, then -1. That one number is the "sign" cell in section 1's picture.

Try it. Open guards, drop them, and see what the card says:

the sign's number: 0

When the rule breaks

With plain references, breaking the rule means the program doesn't compile. Here the program compiles fine, runs, and stops at the line where the card says no. Rust calls this a panic. Think of it as the guard pulling the alarm.

Compiles, then stops while running

let node = RefCell::new(TreeNode::new(1));
let look = node.borrow();
node.borrow_mut().val = 2; // stops here
println!("{}", look.val);
RefCell already borrowed

look is still alive (it's used on the last line), so its tick is still on the card when the working tag goes for the door.

The other way round gets a different message:

Compiles, then stops while running

let node = RefCell::new(TreeNode::new(1));
let mut work = node.borrow_mut();
work.val = 2;
println!("{}", node.borrow().val); // stops here
RefCell already mutably borrowed

Two messages, one meaning: a guard you forgot about is still open on that door. When you see either one, the question is always the same. Which guard is still alive, and why?

That's the trade RefCell makes. The compiler can't follow copied keys around a running program, so it handed the job to the card. You get freedom to share, and you pay for it with mistakes that show up at runtime instead of compile time.

The fix is nearly always to close a door sooner. Copy out what you need, let the guard go, then do the next thing:

let v = node.borrow().val; // look, copy the number, close the door
node.borrow_mut().val = v * 2; // now the door is free for work

judgmentThis one habit prevents most alarms in tree code: open the door, take what you need (a number, a key copy), close the door, then act. The rest of this page keeps coming back to it.

There's also try_borrow_mut(), which hands back an error instead of stopping the program. Tree code almost never needs it. If your code can reach a door that's already open, the fix is to change the code so it can't.

3

Looking

Most tasks only read. You walk through, come back with a number, and the tree is just as you found it. Like a museum: walk through every room, count the paintings, touch nothing. Every room here has two more doors in it.

You're handed a key to the top. The tempting move is to write the recursive function to take keys as well, passing n.left.clone() down each time. That works. It also copies a key on the way into every call and drops it on the way out, which buys nothing. Pass a look at the hook instead:

fn count(node: &Option<Rc<RefCell<TreeNode>>>) -> i32 {
    match node {
        None => 0,
        Some(rc) => {
            let n = rc.borrow();
            1 + count(&n.left) + count(&n.right)
        }
    }
}

pub fn count_nodes(root: Option<Rc<RefCell<TreeNode>>>) -> i32 {
    count(&root)
}

Slowly, because nearly everything on this page is built from this shape:

  • node: &Option<Rc<RefCell<TreeNode>>> is a look at a hook. Not a key. Calling count copies 8 bytes of address and touches no tally.
  • match node on a reference to an Option gives you either None or Some(rc), and rc is a look at the key, a &Rc<...>. Still nothing copied.
  • rc.borrow() puts a tick on the door and hands back the guard n.
  • &n.left is a look at the left hook, reached through the guard.
  • n lives to the end of the arm. So the tick stays on this door while both children get counted, and comes off as the call returns.

The public function takes the key it was given and passes a look at it. One key at the top, looks all the way down.

Looks never get in each other's way, so this costs nothing. It does mean one thing to remember for later: in the middle of a walk, every ancestor of where you are has a tick on its door. Nobody can hang a working tag on any of them until the walk climbs back past.

Same shape with if let:

fn sum(node: &Option<Rc<RefCell<TreeNode>>>) -> i64 {
    if let Some(rc) = node {
        let n = rc.borrow();
        n.val as i64 + sum(&n.left) + sum(&n.right)
    } else {
        0
    }
}

The as i64 is there because values are i32, and a few thousand of them can add up past the two billion an i32 holds.

The copying version

fn count_copying(node: Option<Rc<RefCell<TreeNode>>>) -> i32 {
    match node {
        None => 0,
        Some(rc) => {
            let n = rc.borrow();
            1 + count_copying(n.left.clone()) + count_copying(n.right.clone())
        }
    }
}

judgmentThis compiles, and the answer's the same. Each call costs one tally going up and one coming down. Section 14 measured it: on a tree small enough to sit in the cache, this version took about 40 percent longer than count. Not a disaster. Just a cost with nothing bought.

Two trees at once

Pairs of hooks get matched together, as a tuple of looks:

fn same_shape(
    a: &Option<Rc<RefCell<TreeNode>>>,
    b: &Option<Rc<RefCell<TreeNode>>>,
) -> bool {
    match (a, b) {
        (None, None) => true,
        (Some(x), Some(y)) => {
            let x = x.borrow();
            let y = y.borrow();
            same_shape(&x.left, &y.left) && same_shape(&x.right, &y.right)
        }
        _ => false,
    }
}

Same shape and the values don't matter. Swap which hooks get compared (x.left against y.right) and you're checking whether one tree is the mirror image of the other. Compare values too and you're checking the trees are identical. Passing the same tree as both a and b is fine, by the way: every door gets two ticks at once, and ticks never conflict.

Hand back a look from inside a node, and it doesn't compile

fn left_of(rc: &Rc<RefCell<TreeNode>>) -> &Option<Rc<RefCell<TreeNode>>> {
    &rc.borrow().left // a look that outlives the open door
}

The guard made by rc.borrow() is gone once the function returns, and a look into the node can't outlast the tick that allowed it. The door would be closed with your hand still inside. Hand back a key copy:

fn left_of(rc: &Rc<RefCell<TreeNode>>) -> Option<Rc<RefCell<TreeNode>>> {
    rc.borrow().left.clone() // hand back a key copy, not a look
}

Older code you'll run into

Tree code written for the 2021 edition of Rust is full of odd extra lines, like ending a function with let v = n.borrow().val; v instead of just n.borrow().val. That's because the 2021 edition held guards longer in two places.

factWe compiled both editions. Under 2021, a function whose last line was node.borrow().val (with node a local variable) didn't compile, and an if let whose else branch called borrow_mut() on the same node stopped with the alarm. Under 2024 both work: the guard goes before the locals, and before the else.

Two things did not change. A guard made on the first line of a match or a while let stays alive through the entire body. Write match node.borrow().left.clone() {...} and the tick stays on node until the closing brace. If any arm wants to work on node, take the key copy into a let first, on its own line.

4

Carrying things down

Some answers depend on the path from the top. How deep am I? What do the values above me add up to? Has this value appeared above me already? The node can't see any of that by itself. Whoever calls it has to bring it along.

Think of exploring a cave with two things on you. Some numbers are written on your hand: how deep you are, your running total. Every side passage you go down gets its own copy, so there's nothing to undo when you come back. And there's a bag of breadcrumbs, shared. Drop one as you enter a chamber, pick it back up as you leave, and the bag always holds exactly the path from the entrance to where you're standing.

Numbers on your hand are plain parameters, passed by value. The bag is a &mut. Here are both in one walk:

fn best_leaf_sum(
    node: &Option<Rc<RefCell<TreeNode>>>,
    above: i64,
    best: &mut i64,
) {
    if let Some(rc) = node {
        let n = rc.borrow();
        let here = above + n.val as i64;
        if n.left.is_none() && n.right.is_none() && here > *best {
            *best = here;
        }
        best_leaf_sum(&n.left, here, best);
        best_leaf_sum(&n.right, here, best);
    }
}

pub fn largest_leaf_sum(root: Option<Rc<RefCell<TreeNode>>>) -> i64 {
    let mut best = i64::MIN;
    best_leaf_sum(&root, 0, &mut best);
    best
}

above and here are copied into each call. best is one i64, living in the caller's stack frame, and every call holds a &mut to those same 8 bytes. Starting it at i64::MIN means the first leaf always wins. Decide on purpose what an empty tree should answer; here it's i64::MIN, which may or may not be what you want.

The path itself

fn walk(
    node: &Option<Rc<RefCell<TreeNode>>>,
    path: &mut Vec<i32>,
    out: &mut Vec<Vec<i32>>,
) {
    if let Some(rc) = node {
        let n = rc.borrow();
        path.push(n.val); // drop a crumb on the way in
        if n.left.is_none() && n.right.is_none() {
            out.push(path.clone()); // copies numbers, not nodes
        }
        walk(&n.left, path, out);
        walk(&n.right, path, out);
        path.pop(); // pick it up on the way out
    }
}

Push on the way in, pop on the way out, and the push and the pop sit in the same call, so they can't get out of step. The one clone in there, path.clone(), copies a Vec of numbers when a full path needs keeping. No node is ever copied, and no key either.

Paths as strings work the same way. A String doesn't pop a whole number, so remember the length before you add and cut back to it after:

fn spell(
    node: &Option<Rc<RefCell<TreeNode>>>,
    s: &mut String,
    out: &mut Vec<String>,
) {
    if let Some(rc) = node {
        let n = rc.borrow();
        let mark = s.len();
        s.push_str(&n.val.to_string());
        if n.left.is_none() && n.right.is_none() {
            out.push(s.clone());
        }
        s.push(' ');
        spell(&n.left, s, out);
        spell(&n.right, s, out);
        s.truncate(mark); // back to exactly what the caller had
    }
}

Undoing a map

Sometimes the bag is a HashMap: values seen above, how many times each. The undo step is where this goes wrong. Instead of subtracting one on the way out, remember what was there and put that back:

// How many nodes repeat a value that already appeared above them?
fn repeats(
    node: &Option<Rc<RefCell<TreeNode>>>,
    seen: &mut HashMap<i32, i32>,
) -> i32 {
    match node {
        None => 0,
        Some(rc) => {
            let n = rc.borrow();
            let before = *seen.get(&n.val).unwrap_or(&0);
            seen.insert(n.val, before + 1);
            let below = repeats(&n.left, seen) + repeats(&n.right, seen);
            seen.insert(n.val, before); // undo, exactly as it was
            let here = if before > 0 { 1 } else { 0 };
            here + below
        }
    }
}

Restoring before can't drift, even if a value shows up several times on one path. Running totals with a HashMap of sums seen so far work the same way: insert on the way in, restore on the way out.

A bookmark into a list

One more thing worth carrying: a position in a list that every call reads from in order. Here, checking whether a tree's preorder (node, then left, then right) matches a given list:

fn matches(
    node: &Option<Rc<RefCell<TreeNode>>>,
    want: &[i32],
    pos: &mut usize,
) -> bool {
    match node {
        None => true,
        Some(rc) => {
            let n = rc.borrow();
            if *pos >= want.len() || want[*pos] != n.val {
                return false;
            }
            *pos += 1;
            matches(&n.left, want, pos) && matches(&n.right, want, pos)
        }
    }
}

pub fn preorder_is(
    root: Option<Rc<RefCell<TreeNode>>>,
    want: Vec<i32>,
) -> bool {
    let mut pos = 0;
    matches(&root, &want, &mut pos) && pos == want.len()
}

pos only moves forward, and every call shares it, so it's a &mut usize. Section 9 builds trees with it.

modelOn the machine side: each call's stack frame holds its own copies of the by-value numbers, plus one 8-byte address for each &mut. (An optimizing compiler may keep some of these in registers instead.) A walk 1,000 levels deep has 1,000 frames on the stack, and still only one path vector on the heap.

5

Answers that travel up

The other direction. Plenty of questions about a node can't be answered until its children have answered first. How tall is this subtree? What does it add up to? Is everything below in order? The children go first, report back, and the parent combines what it heard.

An org chart works this way. Every manager collects one summary from each person below them, and sends one summary up.

Sometimes one number isn't enough of a summary.

Take this task: choose as many nodes as you can, with the rule that no chosen node may have a chosen child. A node can't decide alone. It needs to know two things about each child: the best that child's subtree can do if the child is chosen, and the best if it isn't. So every call sends up a pair:

// Choose nodes so that no chosen node has a chosen child.
// Returns (most chosen if this node is chosen, most chosen if it is not).
fn pick(node: &Option<Rc<RefCell<TreeNode>>>) -> (i32, i32) {
    match node {
        None => (0, 0),
        Some(rc) => {
            let n = rc.borrow();
            let (l_take, l_skip) = pick(&n.left);
            let (r_take, r_skip) = pick(&n.right);
            let take = 1 + l_skip + r_skip;
            let skip = l_take.max(l_skip) + r_take.max(r_skip);
            (take, skip)
        }
    }
}

pub fn most_chosen(root: Option<Rc<RefCell<TreeNode>>>) -> i32 {
    let (take, skip) = pick(&root);
    take.max(skip)
}

If this node is chosen, neither child can be, so it adds its children's "not chosen" numbers. If it isn't chosen, each child is free to do whichever is better. Two numbers out of every call, and the whole tree gets solved in one walk. A pair of i32s is 8 bytes, the same size as a key, and it comes back from the call like any other value.

What the parent can use, and what it can't

Sometimes the best answer lives somewhere in the middle of the tree and the parent can't use it at all. Take the longest walk between any two nodes:

// Longest walk between any two nodes, counted in nodes.
fn tall(node: &Option<Rc<RefCell<TreeNode>>>, best: &mut i32) -> i32 {
    match node {
        None => 0,
        Some(rc) => {
            let n = rc.borrow();
            let l = tall(&n.left, best);
            let r = tall(&n.right, best);
            if l + r + 1 > *best {
                *best = l + r + 1; // a walk that bends at this node
            }
            1 + l.max(r) // what the parent can use: one side only
        }
    }
}

A walk through the tree can only bend once, at its highest node. So each node does two different jobs. It records the walk that bends at itself, left height plus right height plus one, in best. And it hands its parent only something the parent can extend: the taller of its two sides, as a straight line. Two jobs, two channels. The return value goes up, the record goes into the bag from section 4.

Mixing those up is the usual bug here. If a node returns the bent walk, its parent will try to extend a walk that already turns, and the answer comes out too big.

What should an empty subtree say?

A height of 0 for an empty subtree is natural. A smallest value isn't: an empty subtree has no smallest value. Option says so honestly:

// Smallest and largest value below and including this node.
// An empty subtree has no values at all, so it answers None.
fn range(
    node: &Option<Rc<RefCell<TreeNode>>>,
    best: &mut i64,
) -> Option<(i32, i32)> {
    match node {
        None => None,
        Some(rc) => {
            let n = rc.borrow();
            let mut lo = n.val;
            let mut hi = n.val;
            if let Some((a, b)) = range(&n.left, best) {
                lo = lo.min(a);
                hi = hi.max(b);
            }
            if let Some((a, b)) = range(&n.right, best) {
                lo = lo.min(a);
                hi = hi.max(b);
            }
            let spread = hi as i64 - lo as i64; // can exceed i32
            if spread > *best {
                *best = spread;
            }
            Some((lo, hi))
        }
    }
}

The other common trick is to have empty subtrees report (i32::MAX, i32::MIN), chosen so any real value beats both in a min or a max. That works too, with one weak spot: a tree that really contains i32::MAX looks the same as an empty one. The Option version can't be fooled. Either way, pick what "empty" reports before you write the combining step, because everything else follows from it.

And notice the i64 in spread. The gap between the largest and smallest i32 is about four billion, which no i32 can hold.

6

Level by level

Recursion goes deep before it goes wide. It finishes everything under the left child before it ever looks right. Some tasks want the opposite order: the top, then everything one step down, then everything two steps down. Anything phrased in levels, rows, or "nearest first" wants this.

Picture a deli counter with a ticket line. Whoever's at the front gets served, and on the way out they hand in tickets for their two children, who join the back of the line. The line always serves a whole generation before the next one gets to the front.

The line is a VecDeque, a ring buffer where pushing onto the back and popping off the front are both cheap. The tickets are keys, Rc<RefCell<TreeNode>>. Here, for the first time on this page, copying keys is the point: a node in the queue is held by two things at once, its parent's hook and its place in line.

fn level_sums(root: Option<Rc<RefCell<TreeNode>>>) -> Vec<i64> {
    let mut out = Vec::new();
    let mut q = VecDeque::new();
    if let Some(r) = root {
        q.push_back(r);
    }
    while !q.is_empty() {
        let width = q.len();
        let mut total = 0;
        for _ in 0..width {
            let node = q.pop_front().unwrap();
            let n = node.borrow();
            total += n.val as i64;
            if let Some(l) = &n.left {
                q.push_back(Rc::clone(l));
            }
            if let Some(r) = &n.right {
                q.push_back(Rc::clone(r));
            }
        }
        out.push(total);
    }
    out
}

Step through it and watch the brass tallies. Every push_back(Rc::clone(l)) takes a tally from 1 to 2. Popping doesn't change anything, because popping moves a key, it doesn't copy one.

This run was handed the only key to the top, which is why lockers get freed as it goes: once a node's turn ends, nothing holds a key to it. Had the caller kept a key of its own, every tally would be one higher and nothing would be freed. Either way the answer is the same. The difference is who's still holding the tree afterward.

for _ in 0..width is what keeps the levels apart. At the top of each round the queue holds exactly one level, so count it first, serve that many, and whoever joins during the round waits for the next one. Without width you'd still visit nodes in level order, you just couldn't tell where one level ends.

Same skeleton, other questions. The first node served each round is the leftmost on its level. The last one is the rightmost. Keep a running max instead of a total, or push values into a Vec per level, and you have most level questions covered.

Numbering the places on a level

Some questions care where on a level a node sits, empty spots included. Number the places: if a node is at place i, its children go at 2i and 2i + 1. The queue holds pairs now, a key and a place:

// For each level: how many places between its first and last node are
// empty?
fn gaps(root: Option<Rc<RefCell<TreeNode>>>) -> Vec<u64> {
    let mut out = Vec::new();
    let mut q: VecDeque<(Rc<RefCell<TreeNode>>, u64)> = VecDeque::new();
    if let Some(r) = root {
        q.push_back((r, 0));
    }
    while !q.is_empty() {
        let width = q.len();
        let mut first = 0;
        let mut last = 0;
        for k in 0..width {
            let (node, place) = q.pop_front().unwrap();
            if k == 0 {
                first = place;
            }
            last = place;
            let i = place - first; // renumber from zero on every level
            let n = node.borrow();
            if let Some(l) = &n.left {
                q.push_back((Rc::clone(l), 2 * i));
            }
            if let Some(r) = &n.right {
                q.push_back((Rc::clone(r), 2 * i + 1));
            }
        }
        out.push(last - first + 1 - width as u64);
    }
    out
}

Places double with every level, so on a long thin tree they outgrow even a u64 after 64 levels. Renumbering from zero at the start of each level, the place - first line, keeps the numbers small when a level's nodes sit near each other. It can't save you when a level really does span more than 264 places, so check the size limits a task gives you before trusting it.

You can also queue Options, pushing n.left.clone() whether or not it's None. Then the queue shows where the gaps are, in order. Handy when the question is about shape.

7

Your own stack

Recursion keeps its to-do list on the call stack: every call waiting for a child to finish is a frame on that stack. You can keep the list yourself, as a pile of bookmarks in a Vec.

Why bother, when recursion is shorter? Two reasons. The pile lives on the heap, which is far larger than the stack, so a very deep tree can't overflow it (section 14 has the numbers). And a loop can stop the moment it has what it needs, or pause between iterations and pick up later. Section 13 depends on that.

fn preorder(root: Option<Rc<RefCell<TreeNode>>>) -> Vec<i32> {
    let mut out = Vec::new();
    let mut stack = Vec::new();
    if let Some(r) = root {
        stack.push(r);
    }
    while let Some(node) = stack.pop() {
        let n = node.borrow();
        out.push(n.val);
        if let Some(r) = &n.right {
            stack.push(Rc::clone(r)); // right goes in first,
        }
        if let Some(l) = &n.left {
            stack.push(Rc::clone(l)); // so left comes out first
        }
    }
    out
}

Node first, then left, then right: preorder. A stack hands back the last thing you put on it, so push right before left.

Inorder (left, node, right) needs a cursor as well as the pile. Walk left as far as you can, putting every node you pass on the pile. Then take the top one, use it, step once to its right, and do the same again:

fn inorder(root: Option<Rc<RefCell<TreeNode>>>) -> Vec<i32> {
    let mut out = Vec::new();
    let mut stack: Vec<Rc<RefCell<TreeNode>>> = Vec::new();
    let mut cur = root;
    loop {
        while let Some(node) = cur {
            cur = node.borrow().left.clone(); // read the next key first
            stack.push(node); // then hand this one to the stack
        }
        match stack.pop() {
            None => break,
            Some(node) => {
                out.push(node.borrow().val);
                cur = node.borrow().right.clone();
            }
        }
    }
    out
}

Look at the order of the two lines inside while let. cur = node.borrow().left.clone() reads the next key out of node first. Only then does stack.push(node) hand node over.

Swap those two lines, and it doesn't compile

while let Some(node) = cur {
    stack.push(node); // the key goes to the stack...
    cur = node.borrow().left.clone(); // ...so it is not here to use
}

Once the key is on the pile it's not in node anymore, so there's nothing to open. Either read first, as above, or push a copy with stack.push(Rc::clone(&node)). Reading first costs nothing.

Postorder (left, right, node) is fiddlier without recursion. The usual way out: run the preorder loop with left and right swapped, which gives node, right, left, then reverse the output.

Every key on the pile is a copy, or a key that moved there, so a node on the pile can't be freed while it waits. Same as the queue. Both are just a different order of service.

8

Ordered trees

Some trees come with a promise: everything hanging off a node's left hook is smaller than it, and everything off its right hook is bigger. At every node, all the way down. A game of higher-or-lower, where each locker tells you which way to go.

Two consequences do almost all the work.

An inorder walk (section 7, or the recursive version: left, node, right) visits the values in sorted order. And finding a value only ever follows one path from the top, discarding half of what's left at every step.

Checking the promise

Comparing each node with its parent isn't enough. A node down in the left half has to be smaller than its parent and smaller than the top as well. So carry the window of allowed values down, section 4 style:

fn ordered(node: &Option<Rc<RefCell<TreeNode>>>, lo: i64, hi: i64) -> bool {
    match node {
        None => true,
        Some(rc) => {
            let n = rc.borrow();
            let v = n.val as i64;
            lo < v
                && v < hi
                && ordered(&n.left, lo, v) // left side: below v
                && ordered(&n.right, v, hi) // right side: above v
        }
    }
}

pub fn is_ordered(root: Option<Rc<RefCell<TreeNode>>>) -> bool {
    ordered(&root, i64::MIN, i64::MAX)
}

Going left shrinks the window from above, going right shrinks it from below. The bounds are i64 so that a node holding i32::MIN or i32::MAX still fits strictly inside the starting window. Option<i32> bounds, with None for "no limit," do the same job.

Walking one path

No recursion needed when you only go down one path. A cursor will do, holding one key at a time:

// Smallest value that is at least x, if there is one.
fn ceiling(root: &Option<Rc<RefCell<TreeNode>>>, x: i32) -> Option<i32> {
    let mut best = None;
    let mut cur = root.clone();
    while let Some(node) = cur {
        let n = node.borrow();
        if n.val == x {
            return Some(x);
        }
        if n.val > x {
            best = Some(n.val); // a candidate; anything better is to the left
            cur = n.left.clone();
        } else {
            cur = n.right.clone();
        }
    }
    best
}

Each step copies one key into cur and drops the old one when node goes away at the end of the iteration. Only the current node carries a tick. Notice cur = n.left.clone() runs while n is still open on node: that's fine, because cur is a different variable from node. The key in cur was moved into node at the top of the loop.

Skipping what can't matter

When a node is below the range you want, everything on its left is even further below. Skip that side entirely:

// How many values fall in lo..=hi?
fn within(node: &Option<Rc<RefCell<TreeNode>>>, lo: i32, hi: i32) -> i32 {
    match node {
        None => 0,
        Some(rc) => {
            let n = rc.borrow();
            if n.val < lo {
                return within(&n.right, lo, hi); // left side is smaller still
            }
            if n.val > hi {
                return within(&n.left, lo, hi); // right side is bigger still
            }
            1 + within(&n.left, lo, hi) + within(&n.right, lo, hi)
        }
    }
}

The value just before

An inorder walk visits values in sorted order, so a prev carried across calls (section 4's bag again) always holds the value just below the current one:

// Largest gap between two neighbors in sorted order.
fn gap(
    node: &Option<Rc<RefCell<TreeNode>>>,
    prev: &mut Option<i32>,
    best: &mut i64,
) {
    if let Some(rc) = node {
        let n = rc.borrow();
        gap(&n.left, prev, best);
        if let Some(p) = *prev {
            let d = n.val as i64 - p as i64;
            if d > *best {
                *best = d;
            }
        }
        *prev = Some(n.val);
        gap(&n.right, prev, best);
    }
}

Any question about neighbors in sorted order (closest pairs, gaps, duplicates, runs of equal values) is this walk with a different line in the middle.

9

Building

A new node takes three wrappings: the node in a RefCell, that in an Rc, that in Some. Typing all three every time gets old fast, so make a helper:

fn node(
    val: i32,
    left: Option<Rc<RefCell<TreeNode>>>,
    right: Option<Rc<RefCell<TreeNode>>>,
) -> Option<Rc<RefCell<TreeNode>>> {
    Some(Rc::new(RefCell::new(TreeNode { val, left, right })))
}
let tree = node(4, node(2, None, None), node(7, None, None));

Each call to node is one trip to the allocator for 48 bytes.

Look at the order things happen in. The children are built first, then passed straight into the parent's struct. Nothing ever gets changed after it's made, so nothing ever needs a working tag. That's worth aiming for. Build bottom-up and the sign on the door never comes into it.

Middle on top

From a sorted list, the shortest tree puts the middle value on top, then does the same with each half. Divide and conquer, children first:

// A tree of the smallest height from sorted values: middle on top.
fn from_sorted(
    v: &[i32],
    lo: usize,
    hi: usize,
) -> Option<Rc<RefCell<TreeNode>>> {
    if lo >= hi {
        return None; // the range lo..hi is empty
    }
    let mid = lo + (hi - lo) / 2;
    let left = from_sorted(v, lo, mid);
    let right = from_sorted(v, mid + 1, hi);
    Some(Rc::new(RefCell::new(TreeNode {
        val: v[mid],
        left,
        right,
    })))
}

The range is half-open: lo..hi includes lo and stops just before hi. With that convention, the left half is lo..mid, the right half is mid + 1..hi, and an empty range is simply lo >= hi. No mid - 1 anywhere.

factWhy avoid mid - 1? Indices are usize, and usize can't go below zero. We ran 0usize - 1: a debug build stopped with "attempt to subtract with overflow," and a release build quietly produced 18446744073709551615.

If the values arrive as a linked list, copy them into a Vec first. Building wants to jump straight to the middle, and a list can only walk.

When you keep needing to know where some value sits in a list (say, while rebuilding a tree from two different listings of it), build a HashMap<i32, usize> from value to position once, instead of searching every time.

Reading a list in order while you build

Section 4's shared bookmark builds trees too. Here the list is a preorder walk with None wherever a hook was empty:

// Preorder, with None standing in for every empty hook.
fn rebuild(
    items: &[Option<i32>],
    pos: &mut usize,
) -> Option<Rc<RefCell<TreeNode>>> {
    let item = items[*pos];
    *pos += 1;
    match item {
        None => None,
        Some(v) => {
            let left = rebuild(items, pos);
            let right = rebuild(items, pos);
            Some(Rc::new(RefCell::new(TreeNode {
                val: v,
                left,
                right,
            })))
        }
    }
}

Each call reads one entry and moves the bookmark on. A Some means "a node here, then its left subtree, then its right." A None means "empty hook, nothing more to read for it." The list's own shape tells every call how much to consume.

Attaching after the fact

Sometimes you can't build bottom-up, because pieces arrive in some order you don't control. Then you make nodes first and hang them on hooks later, which means working tags and copied keys.

Hang your only key on a hook and keep using it, and it doesn't compile

let child = Rc::new(RefCell::new(TreeNode::new(2)));
let parent = Rc::new(RefCell::new(TreeNode::new(1)));
parent.borrow_mut().left = Some(child); // the only key goes on the hook
child.borrow_mut().val = 20; // nothing left in `child`

Some(child) moved the key onto the hook. child is empty now. If you still need to reach the child yourself, the hook gets a copy and you keep yours:

let child = Rc::new(RefCell::new(TreeNode::new(2)));
let parent = Rc::new(RefCell::new(TreeNode::new(1)));
parent.borrow_mut().left = Some(Rc::clone(&child)); // a copy goes on the hook
child.borrow_mut().val = 20; // `child` still holds its own key

Two houses, one wall

Nothing says a node can only hang in one place. Copy the key, hang it on two hooks:

let wall = node(9, None, None);
let house_a = node(1, wall.clone(), None); // copy of the key
let house_b = node(2, None, wall.clone()); // another copy
// the 9 now has three keys: `wall` and one hook in each house

if let Some(w) = &wall {
    w.borrow_mut().val = 0; // change it once...
}
// ...and both houses see 0 under them

Legal, and sometimes exactly right. When you have to produce many trees that share pieces (every possible shape of a given size, say), building each small piece once and hanging copies of its key saves a great deal of allocating.

judgmentIt's safe as long as nobody rewires a shared piece afterward. A shared wall belongs to both houses. Knock it down for one and the other loses it too. If anything later on will change the trees, build each one its own pieces.

10

Rewiring

Now the working tag earns its place. Think of a tree surgeon: tag the door so nobody wanders in, lift branches off their hooks, hang them back where they belong, take the tag down on the way out.

The lifting is take(), the same as with lists. It lifts the key off a hook, hands it to you, and leaves an honest None behind. Here's a tree mirrored left to right, in place:

fn mirror(node: &Option<Rc<RefCell<TreeNode>>>) {
    if let Some(rc) = node {
        let mut n = rc.borrow_mut();
        let left = n.left.take();
        let right = n.right.take();
        n.left = right;
        n.right = left;
        mirror(&n.left);
        mirror(&n.right);
    }
}

Two things to watch in the stepper.

First, the tallies never change. Every key moves from a hook to your hand and back to a hook. Nothing is copied, nothing allocated, nothing freed.

Second, the working tags pile up along the path, one on every door from the top down to wherever the walk is, just like the ticks did in section 3. That's allowed. Every tag is on a different door. The call on 2 can't touch 4's door while 4's tag is up, but it doesn't need to.

Swap the two hooks directly through the guard, and it doesn't compile

if let Some(rc) = node {
    let mut n = rc.borrow_mut();
    std::mem::swap(&mut n.left, &mut n.right); // two loans from one guard
}

Every field you reach through a guard goes through the guard itself. So &mut n.left and &mut n.right look to the compiler like two separate &mut borrows of n, at the same time. Turn the guard into one plain &mut TreeNode first. Then the compiler sees two different fields of one struct, which is fine:

fn mirror_swap(node: &Option<Rc<RefCell<TreeNode>>>) {
    if let Some(rc) = node {
        let mut guard = rc.borrow_mut();
        let n = &mut *guard; // one plain &mut TreeNode from the guard
        std::mem::swap(&mut n.left, &mut n.right);
        mirror_swap(&n.left);
        mirror_swap(&n.right);
    }
}

Both versions are correct. take() twice is plainer to read, the reborrow is shorter. Pick either.

Return what should hang here

Pruning, inserting and deleting all share one shape. The function takes a key and returns a key, or None, meaning "nothing hangs here anymore." The parent takes its hook's key, hands it in, and hangs up whatever comes back:

n.left = cut_negative(n.left.take());

// Remove every subtree in which all values are negative.
fn cut_negative(
    node: Option<Rc<RefCell<TreeNode>>>,
) -> Option<Rc<RefCell<TreeNode>>> {
    match node {
        None => None,
        Some(rc) => {
            let goes = {
                let mut n = rc.borrow_mut();
                n.left = cut_negative(n.left.take());
                n.right = cut_negative(n.right.take());
                n.val < 0 && n.left.is_none() && n.right.is_none()
            }; // the working tag comes down here
            if goes { None } else { Some(rc) }
        }
    }
}

Read the block in the middle. The guard n is made inside its own { ... }, the children are re-hung, and the block's value (cut or keep?) is copied out into goes. The block ends, the guard goes, the tag comes down. Only then does Some(rc) hand the key back to the caller.

Hand the key back while its door is still open, and it doesn't compile

fn cut_negative(
    node: Option<Rc<RefCell<TreeNode>>>,
) -> Option<Rc<RefCell<TreeNode>>> {
    match node {
        None => None,
        Some(rc) => {
            let mut n = rc.borrow_mut();
            n.left = cut_negative(n.left.take());
            n.right = cut_negative(n.right.take());
            if n.val < 0 && n.left.is_none() && n.right.is_none() {
                None
            } else {
                Some(rc) // handing the key over while `n` is still open
            }
        }
    }
}

Without the inner block, n lives to the end of the arm. It's a guard on rc's door, so rc can't be given away while n is still around. You'd be handing someone a key to a door you're still standing in.

The same shape covers the other two. To insert, walk to the right None hook and return a fresh node there; every other call returns the key it was given. To delete, return whatever should take the deleted node's place. Every parent re-hangs what comes back, so the top of the tree can change too, with no special case.

Changing values, not shape

When the shape stays and only numbers change, there's no taking. Just open the door for work and write:

// Each value becomes the sum of every value at or below it in sorted order.
fn running(node: &Option<Rc<RefCell<TreeNode>>>, total: &mut i64) {
    if let Some(rc) = node {
        let mut n = rc.borrow_mut();
        running(&n.left, total);
        *total += n.val as i64;
        n.val = *total as i32;
        running(&n.right, total);
    }
}

Visiting in sorted order, keeping a running total in section 4's bag, writing it back into each node. Reverse the walk (right before left) and the total runs from the top down instead.

Same door, different door

Compiles, then stops while running

let n = node.borrow();
if let Some(l) = &n.left {
    l.borrow_mut().val = n.val; // fine: a different door
}
node.borrow_mut().val = 0; // stops: `n` is still open on this door
RefCell already borrowed

Working on the child while you look at the parent is fine: different doors. Working on the parent while your own look is still open on it isn't. This happens easily in level walks, where you've got n open on a node and want to change something about that same node. Copy out what you need from n, let it go (drop(n), or end its block), then open the door again for work.

11

The same node, not an equal one

Identical twins look the same, sound the same, maybe even answer to the same nickname. They're still two people. Two keys to the same locker are the other situation: one locker, reached two ways.

With keys you can copy, both situations come up, and Rust has a separate question for each:

let a = node(5, node(1, None, None), None);
let b = node(5, node(1, None, None), None); // built separately
let c = a.clone(); // a second key to a's locker

println!("{} {}", a == b, a == c); // true true

let ka = a.as_ref().unwrap(); // Rc::ptr_eq wants two &Rc
let kb = b.as_ref().unwrap();
let kc = c.as_ref().unwrap();
println!("{} {}", Rc::ptr_eq(ka, kb), Rc::ptr_eq(ka, kc)); // false true

== on these types compares contents. The #[derive(PartialEq)] on TreeNode compares the value and then both hooks, and comparing hooks compares whatever hangs on them, all the way to the bottom. So a == b opens both doors at every node of both subtrees. For two big trees that's a full walk of each.

factOne shortcut is built in. When both sides are keys to the same locker, == notices and answers true without opening anything. We checked: comparing two keys to one node while its working tag was up gave no alarm. The same comparison between two different lockers set it off.

Rc::ptr_eq compares two addresses. Two numbers, one comparison, no doors opened.

Which one a task wants depends on what it's asking. "Do these two trees hold the same values in the same shape?" is ==, and paying for the full walk is the honest cost of the question. "Is this node the one I was given?" is Rc::ptr_eq.

Handing back a node that's already there

When the answer to a task is a node, you hand back a key to the actual locker:

// A key to the first node, in preorder, that holds x.
fn find(
    node: &Option<Rc<RefCell<TreeNode>>>,
    x: i32,
) -> Option<Rc<RefCell<TreeNode>>> {
    match node {
        None => None,
        Some(rc) => {
            let n = rc.borrow();
            if n.val == x {
                return Some(Rc::clone(rc)); // a key to this very node
            }
            let hit = find(&n.left, x);
            if hit.is_some() {
                return hit;
            }
            find(&n.right, x)
        }
    }
}

That key adds one to the node's tally, and that's the whole cost. The node is still hanging in the tree too. Change it through the key you got back and the tree sees the change, because there's only one locker.

Notice the shape of the two lookups. Ask the left side; if it found something, pass that up untouched. Otherwise ask the right side. Many tasks work this way, every child answering "did you find it?" with a key or a None, and the parent deciding from what came back. When the parent needs both answers, ask both first and match on the pair: (Some(_), Some(_)), (Some(x), None), (None, Some(x)), (None, None). Each case says something different about where the targets are.

Given a key, find where it is

Some tasks hand you keys to nodes inside the tree as well as the top. They're asking about those exact lockers:

// How deep is the node that `target` is a key to? (root is depth 0)
fn depth_of(
    node: &Option<Rc<RefCell<TreeNode>>>,
    target: &Rc<RefCell<TreeNode>>,
    d: i32,
) -> Option<i32> {
    match node {
        None => None,
        Some(rc) => {
            if Rc::ptr_eq(rc, target) {
                return Some(d); // this very locker, not a lookalike
            }
            let n = rc.borrow();
            let hit = depth_of(&n.left, target, d + 1);
            if hit.is_some() {
                return hit;
            }
            depth_of(&n.right, target, d + 1)
        }
    }
}

The Rc::ptr_eq check comes before rc.borrow(): deciding whether this is the target doesn't need to open the door at all. If the task promises that values are unique, comparing val works too and costs about the same. Rc::ptr_eq works either way.

12

Trees as graphs

Hooks only point down. That's fine until a task asks about moving up, or sideways. Everything within two steps of some node, say, where a step can go to a parent as easily as to a child. A node has no idea who its parent is.

The fix is to turn the family tree into a phone tree. Write down, for every person, who they can call: parents and children both. Then forget the tree and walk the phone list.

The obvious way to write that down doesn't work:

Use a key as a HashMap key, and it doesn't compile

let mut depth: HashMap<Rc<RefCell<TreeNode>>, i32> = HashMap::new();
depth.insert(Rc::clone(&rc), 0); // keys can't be filed in a HashMap

A HashMap files every entry under a hash of its key. Rc<RefCell<TreeNode>> doesn't have one, and when you think about it, it couldn't sensibly have one. The obvious hash would come from the node's contents, and those can change any time someone works inside the locker. An entry filed under the old hash would never be found again.

So file the phone list under something that doesn't change. If the task promises values are unique, use the value:

// Every value's neighbors: its parent and its children.
fn link(
    node: &Option<Rc<RefCell<TreeNode>>>,
    parent: Option<i32>,
    adj: &mut HashMap<i32, Vec<i32>>,
) {
    if let Some(rc) = node {
        let n = rc.borrow();
        let mut near = Vec::new();
        if let Some(p) = parent {
            near.push(p);
        }
        if let Some(l) = &n.left {
            near.push(l.borrow().val);
        }
        if let Some(r) = &n.right {
            near.push(r.borrow().val);
        }
        adj.insert(n.val, near);
        link(&n.left, Some(n.val), adj);
        link(&n.right, Some(n.val), adj);
    }
}

The map holds only numbers. No keys copied, no tallies touched, and the tree itself is never needed again. Walk the map with the queue from section 6, holding values instead of keys, plus a HashSet of values already reached so the walk doesn't bounce between parent and child forever. Each round of the queue is one more step away from where you started.

If values can repeat, use the locker's address instead. It's a plain number, so it hashes fine:

let id = Rc::as_ptr(rc) as usize; // the locker's address, as a number

factThat address stays the same for as long as any key to the node exists, because an Rc's block never moves. Once the last key is gone, the address can be handed out again to some other allocation, so only use it while you're holding the tree.

Building from loose pieces

The opposite direction comes up too: you're given a pile of "this value's left child is that value" facts, in no useful order, and have to put the tree together. Keep a map from value to key, making each node the first time its value turns up:

// The node for value v: made on first request, the same one after that.
fn get(
    map: &mut HashMap<i32, Rc<RefCell<TreeNode>>>,
    v: i32,
) -> Rc<RefCell<TreeNode>> {
    if !map.contains_key(&v) {
        map.insert(v, Rc::new(RefCell::new(TreeNode::new(v))));
    }
    Rc::clone(&map[&v])
}
let p = get(&mut map, 10);
let c = get(&mut map, 4);
p.borrow_mut().left = Some(c); // the map still holds its own key to 4

The map holds one key to every node it has ever made. Every hook adds another. Once the tree is assembled, the map can go, and the hooks will keep every node alive by themselves. (Except the top one, which nobody hangs. Keep a key to that.)

13

Nodes that outlive a call

Some tasks aren't a function. They're a struct: built once from a tree, then asked something over and over. next(), then next() again, then has_next(). Between calls, the struct is all there is, so whatever it needs to remember has to be in its fields.

Like a bookmark left in a book between reading sessions. For trees, the bookmarks are keys.

Here's section 7's preorder loop, cut into one step per call:

struct Walker {
    stack: Vec<Rc<RefCell<TreeNode>>>,
}

impl Walker {
    fn new(root: Option<Rc<RefCell<TreeNode>>>) -> Self {
        let mut stack = Vec::new();
        if let Some(r) = root {
            stack.push(r);
        }
        Walker { stack }
    }

    fn next(&mut self) -> i32 {
        let node = self.stack.pop().unwrap();
        let n = node.borrow();
        if let Some(r) = &n.right {
            self.stack.push(Rc::clone(r));
        }
        if let Some(l) = &n.left {
            self.stack.push(Rc::clone(l));
        }
        n.val
    }

    fn has_next(&self) -> bool {
        !self.stack.is_empty()
    }
}

Each call to next does one round of the loop and returns. The pile of keys waits in self.stack until the next call. This is why section 7 bothered with a loop at all: recursion can't stop halfway and come back later, but a loop's state can sit in a struct.

let root = node(1, node(2, None, None), node(3, None, None));
let mut w = Walker::new(root.clone());
drop(root); // the caller lets go of the tree

while w.has_next() {
    print!("{} ", w.next()); // 1 2 3
}

factThat prints 1 2 3. The caller dropped its key to the top before the first next(), and nothing was freed: the tally on the top node went from 2 to 1, not to 0, because the walker's stack held the other key. A tree lives exactly as long as somebody holds a key to it. That somebody doesn't have to be whoever built it.

When the method says &self

You'll sometimes be given method signatures written fn next(&self), often with a note saying you may switch to &mut self if you need to. Switching is the simple fix, since next clearly changes the struct. The other fix is a sign on your own door:

struct QuietWalker {
    stack: RefCell<Vec<Rc<RefCell<TreeNode>>>>, // a sign on our own door
}

impl QuietWalker {
    fn next(&self) -> i32 {
        let mut stack = self.stack.borrow_mut(); // `&self` is enough now
        let node = stack.pop().unwrap();
        let n = node.borrow();
        if let Some(r) = &n.right {
            stack.push(Rc::clone(r));
        }
        if let Some(l) = &n.left {
            stack.push(Rc::clone(l));
        }
        n.val
    }
}

Same idea as the nodes, applied to the struct. Through &self you can only look, so the field that changes wears a RefCell, and the method opens it for work. Same rules, same alarm if two methods ever have it open at once.

Other structs follow the same pattern with different fields. One holds the top of the tree plus a queue of nodes that still have a free hook. Another fills a HashSet of values once in new and only reads it afterward. One has no fields at all, because its methods don't need to remember anything; an empty struct is fine. The rule each time: keys for nodes, plain data for everything else, and a RefCell only if a &self method has to change something.

14

Costs you didn't write

Every line of tree code on this page does a little more than it says. None of it is hidden. It's in the fine print.

  • Every node is 48 bytes. Two counters, the sign, the 24-byte node. The same node behind a Box would be 24.
  • Every key copy adds one to a counter, and every dropped key subtracts one and checks for zero. Plain additions, nothing more. Arc, the version that can be shared between threads, does the same with atomic instructions, which cost more; Rc doesn't pay for that because it can't leave its thread.
  • Every look and every working tag reads the sign, checks it, and writes it. When the guard goes, the sign is written again. So even a read-only walk writes to every node it visits.

Does that add up to anything? We timed six ways of adding up the values in a tree.

Read the small chart first, where the numbers held steady. Moving from a Box tree to an Rc<RefCell> tree cost a bit more than double. How you walked it changed much less: helper, stack and queue all land within about 20 percent of each other. Copying a key into every call was the slowest Rc version, about 40 percent behind the &Option helper.

On the big tree the gap to Box grew to between two and four times, and the walking methods blurred together inside their ranges. And the plain Vec of the same numbers sits far below everything on both charts: about 8 times faster than the Box tree on the small one, 30 times on the big one, and further still past the Rc trees. A tree scatters its values across the heap, and every node visited is a jump to somewhere new.

modelWhy the gap grows on the big tree? Our explanation, not something we measured directly: a 48-byte node is twice as much memory to pull through the cache as a 24-byte one, and the sign gets written on every visit, so even a read-only walk dirties every cache line it touches. When the tree fits in the cache, those writes are cheap. When it doesn't, they all have to go back out to memory.

judgmentNone of this is a reason to avoid the type you're handed. It's a reason to pick the cheap walk when it's equally easy, and to remember that a tree is a slow way to store numbers you could have kept in a Vec.

Running out of stack

Recursion keeps one frame per level on the stack, and the stack is small. We built a tree as one long chain, every node hanging on its parent's left hook, and found where the section 3 count stopped working.

factOn this machine's 8 MiB main-thread stack: in a debug build, counting overflowed the stack at about 65,000 levels. In a release build it lasted until about 261,000.

Then the surprise. Dropping a tree is recursive too. The last key to the top drops the top node, which drops the keys on its hooks, which drop their nodes, and so on down. Your code never wrote a recursive function, but freeing the tree runs one.

factDropping that chain overflowed the stack at about 35,000 nodes in a debug build, sooner than counting it did. In release, about 261,000 again.

Most trees are nowhere near that deep: a balanced tree with a million nodes is only 20 levels. But a task that allows a hundred thousand nodes allows them in one long line. If your code runs fine in release and dies in debug on a big test, this is a likely reason. Section 7's own stack fixes the walking; the dropping you'd have to take apart by hand, node by node, the same way.

When tallies never reach zero

The tally frees a locker when its last key goes. Now hang a key on a hook that points back up:

let a = Rc::new(RefCell::new(TreeNode::new(1)));
let b = Rc::new(RefCell::new(TreeNode::new(2)));
a.borrow_mut().left = Some(Rc::clone(&b));
b.borrow_mut().left = Some(Rc::clone(&a)); // a hook pointing back up

println!("{} {}", Rc::strong_count(&a), Rc::strong_count(&b)); // 2 2
drop(a);
drop(b);
// Each locker still holds a key to the other. Neither tally reaches
// zero, so neither node is ever freed.

factWe counted live bytes before and after: 96 bytes were still allocated after both drops. Two nodes of 48 bytes each, unreachable and never freed. Nothing crashed, and nothing warned us. That's a leak: memory that's lost until the program exits.

Trees you're handed never have cycles. Hooks only point down. But the moment you add a hook pointing up (a parent field, say), every parent and child hold keys to each other and no tally can ever reach zero.

The way out is the second kind of key, the one the weak counter in section 1 counts. A Weak key doesn't count toward keeping a locker alive. To use one you ask to upgrade it to a real key, which only works if the locker still exists:

let child = Rc::new(RefCell::new(TreeNode::new(2)));
let up: Weak<RefCell<TreeNode>> = Rc::downgrade(&child); // not counted
println!("{}", up.upgrade().is_some()); // true: still alive
drop(child);
println!("{}", up.upgrade().is_some()); // false: the locker is gone

Parent links made of Weak keys don't keep anything alive, so the tallies work again. That's as far as this page goes with them.

And when a new task shows up, the first question is which grip it needs.

Is the answer about the whole tree? Look (section 3). If a node needs to know what's above it, carry it down (4). If it needs its subtrees' answers first, send answers up (5). A lot of tasks need both at once, and that's fine: numbers come down in the parameters, answers go up in the return value.

Does the task talk about levels, rows, or what's nearest? Queue (6). Is the tree promised to be in order? Then use the order (8), and expect to follow one path instead of all of them.

Does it want a new tree? Build children first (9). The same nodes in a new shape? Take and re-hang (10). Is the answer a node? Hand back a key to it (11). Does it need to move toward the top, or count steps in every direction? Make a map (12). Is it a struct with methods? Keep keys in the fields (13).

One habit under all of them: open a door, take what you need, close it, then act.
