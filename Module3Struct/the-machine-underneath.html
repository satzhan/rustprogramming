Rust, underneath the syntax

A struct is a name for some bytes.
Running it sets a lot of machinery in motion.

Bundling a few values together and naming them looks like nothing happens at runtime. In fact the bytes get arranged in a specific order, a pointer reaches out to a separate allocation, and requests cross a guarded boundary into the part of the machine a program isn't allowed to touch directly. None of it is visible in the code. The diagrams below show each piece on its own.

01 / WHERE A STRING LIVES

A handle on the stack, bytes on the heap

Write let name = String::from("Alice") and it feels like the word Alice is sitting in the variable. It isn't.

What sits in the variable, on the stack, is three machine words — twenty-four bytes on a 64-bit machine:

  • a pointer — an address out on the heap
  • a length — how many bytes are in use (here, 5)
  • a capacity — how large the allocation is (say 8, leaving room to grow)

The characters A l i c e live somewhere else, out on the heap, where space of any size can be allocated at runtime. The variable is a small fixed-size handle; the data it points to is a separate, variable-size allocation.

That split is what makes a move cheap. Assign the String to another variable and Rust copies the handle — twenty-four bytes — and marks the original invalid. The heap data isn't touched. Two handles pointing at one allocation would set up a double-free, so Rust doesn't allow it: after the move, name is gone. A clone is the other option — it allocates a second buffer and copies the bytes, leaving two independent strings.

The fat pointer ↔ heap bufferowner: name

A move copies the 24-byte handle and invalidates the original. A clone allocates a second buffer and copies the bytes.

std::mem::size_of::<String>() returns 24 on any 64-bit target — three usize words, regardless of the string's length, since the characters are on the heap rather than in the handle. Vec<T> has the same pointer/length/capacity shape and is also 24 bytes.

02 / ALIGNMENT AND PADDING

Why field order can change a struct's size

A field has to sit at an address its type is aligned to. An 8-byte value wants an address that's a multiple of 8; a 2-byte value, a multiple of 2. Aligned reads are a single fetch; unaligned ones cost extra.

To satisfy that, the compiler inserts padding — unused bytes between fields — so each field lands on an address it accepts. Padding is dead space. If a one-byte field comes right before an eight-byte field, seven bytes of padding go in between. Arrange the fields poorly and a struct holding 12 bytes of data can take up 24.

By default, under repr(Rust), the compiler reorders the fields itself — largest alignment first — to remove most of that padding. Rearranging the declaration changes nothing, because the compiler has already chosen a good order; the exact layout isn't guaranteed and can differ between compiler versions. Field order only matters once you opt out with #[repr(C)], which keeps fields in declared order so the bytes line up with a C struct, a file format, or data on the wire. The two modes are below.

03 / THE USER–KERNEL BOUNDARY

The boundary your program can't cross directly

A program can't touch the disk, the network card, or the screen on its own. Every println!, every file read, every byte that reaches the screen goes through one route.

The CPU runs in two modes. In user mode, where the program runs, those operations are off-limits. In kernel mode, the operating system can do them — talk to hardware, hand out memory, end processes. The hardware enforces the wall between the two.

To get work done on the other side, the program makes a system call. It loads a number identifying the operation into a register — on x86-64 Linux, 1 is write — points at the data, and runs a trap instruction. The trap is the only sanctioned way through the wall. The CPU switches to kernel mode, the kernel runs the handler for that number, does the work, and switches back to user mode at the instruction right after the call. mov rax, 1; syscall is the bare form of this. println! is the same call with the standard library filling in the register setup — there's no other path to the screen.

A write() crossing the user / kernel boundarymode: USER
1load syscall number into rax (1 = write), point rsi at the data
2execute trap — the CPU switches USER → KERNEL mode
3kernel looks up handler #1, performs the privileged write to the device
4return-from-trap — CPU switches KERNEL → USER, you resume exactly where you stopped

The system-call number, the registers used to pass arguments, and the calling convention are all platform-specific. 1 = write holds on x86-64 Linux; the numbers differ on other architectures. The inline-assembly form also requires unsafe and won't assemble on ARM.

04 / BUFFERED I/O

Why buffering makes I/O fast

Crossing into the kernel and back has a fixed cost: save registers, switch modes, run the handler, switch back. Pay it once for a large chunk of data and it's negligible. Pay it per byte and the same work takes hundreds of crossings instead of one.

That cost is the whole reason buffered I/O exists. A buffered writer keeps a block of memory in front of the system call. Writes go into that block — no crossing, just a memory copy. When the block fills, or flush() is called, it makes a single system call and sends everything at once.

BufReader does the reverse: it reads a large block in one call and hands it back in small pieces, so a loop reading a line at a time isn't making a system call per line. In both cases the number of boundary crossings is what changes. The counter below shows it for a 13-character write.

05 / SPAWNING A PROCESS

fork, then exec

When a Rust program runs Command::new("python").spawn(), two older system calls do the work on Unix.

First fork: the operating system makes a near-exact copy of the calling process. For a moment two processes exist with the same code and memory, told apart by their process IDs. Then exec: the child replaces its own program image with a different one — same process, new program. After fork and then exec, the child is running Python.

The two processes still need to exchange data, and a file is one way to do it. The Rust parent writes log_summary.txt; the Python child reads it and draws a chart. The file is the channel — two separate processes coordinating through a shared resource, which is what inter-process communication is at its simplest.

fork → exec → talk through a file → waitready

fork clones the process · exec swaps the child's program for Python · the file carries the data between them · wait reaps the child.

On Unix, spawn() calls fork() then exec; on Windows it's CreateProcess. A child that has exited but hasn't been wait-ed on stays around as a zombie, keeping its process-ID entry until the parent reaps it. The standard library doesn't reap automatically — not even when the Child handle is dropped — so leaked zombies can eventually exhaust the available process IDs.

06 / METHOD RECEIVERS

Three kinds of self

A method's first parameter says what it does with the struct it belongs to. There are three choices, and each is a different arrangement about who keeps the struct afterward.

&self borrows it to read. &mut self borrows it to change a field. self takes it — the struct moves into the method, and the caller's variable is invalid once the call returns. It's the same borrowing the compiler applies to any other value; here the value happens to be the receiver. After &self or &mut self the caller still owns the struct; after self it doesn't.
