Generics & Traits

Two ideas, one sentence: write a routine once for many types, and use traits to say what those types must be able to do.

Part I

Generics — one routine, many types

1

The itch generics scratch

Here are three functions. Read them closely: they are the same function written three times. The body never changes — only the type in the signature does. Whenever you find yourself copying a routine just to change its type, that is the exact moment a generic replaces all the copies with one.

2

A type that can do nothing

Write <T> with no conditions and you have promised the compiler nothing about T, so the body may do nothing with it. To compare values you must say the type can be compared; to lift one value out of the list you must say it can be copied. Those promises are trait bounds. Toggle them and watch the compiler decide whether the routine is allowed to exist.

When inference runs out: turbofish

    
Usually Rust works out T from how you use the result. Sometimes it

    Part II
Traits — saying what a type can do

  


  
  

    7
    
One ability, many shapes

    
A generic says "any type." Often you need to say something narrower: "any type
      that can do this." That ability is a trait. A rectangle and a
      circle store completely different numbers, yet both can answer one question — what is your
      area? Each answers it its own way, under one shared name.


    

      

        

          
          
        

        
      

      

    


    

  


  
  

    8
    
Three ways to write the same contract

    
Requiring "a type that can do Area" is the same promise you met in
      section 2, now about behavior instead of comparison. Rust gives you three spellings for it.
      They compile to exactly the same thing; pick whichever reads best. When the list of
      requirements grows long, the where clause keeps the signature tidy.


    

      

        
        
        
      

      

      

    

  


  
  

    9
    
A trait can bring its own behavior

    
A trait is not only a list of required methods. It can also supply
      a method, written in terms of the ones you must provide. You implement the small required part;
      you get the larger built-on part for free, and you may still override it when one type wants
      something different.


    

      

        
        
      

      

    


    

  


  
  

    10
    
Putting a trait on a type you didn't write

    
You can implement your own trait for a built-in type, and you can implement a
      built-in trait for your own type. What you cannot do is implement a foreign
      trait on a foreign type — if both belong to someone else, Rust refuses,
      so that two crates can never disagree about the same pairing. The way through is a
      newtype: wrap the foreign type in a one-field struct of your own, and now
      the type is yours to extend.

    11
    
Choosing the type now or later

    
There are two ways to use a trait, and the choice is about when the
      concrete type is settled. With a generic, each call is locked to one type and the compiler
      writes a direct, specialised copy — fastest, but every item in the batch must be the same
      type. With dyn, one collection can hold several different types at once, each
      decided as the program runs. Match the tool to the situation.
