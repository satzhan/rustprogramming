the moment it has two narrators.

Sequential code has exactly one order of events: the one written on the page. The moment a second thread shows up, that guarantee is gone — and most of the strange bugs in this space come from forgetting it disappeared.

01 — the shape of the problem

Three people, three banknotes, no rules

Put three $100 bills on a table. Tell three people to each take one. If they talk to each other first — "you take the left one, I'll take the middle" — it works cleanly, every time. If they don't talk, and just move for whichever bill they see, you get one of two outcomes: it happens to work out, or two people grab the same bill at the same instant and you have a torn banknote and an argument.

Nothing about the room changed between those two outcomes. Same table, same people, same bills. The only thing that changed was the order things happened in — and that order was never written down anywhere. It was decided in the moment, by whoever moved first.

That's the entire shape of concurrent programming. Threads are the people. Shared memory is the table. And the "order things happened in" is something your program's source code does not fully control — the operating system's scheduler has a say too, and it doesn't ask permission.

Worth sitting with: a program with a concurrency bug is not broken the way a program with a typo is broken. It can run correctly a thousand times and fail on the thousand-and-first, with nothing in the code having changed between runs. That's a different category of bug, and it needs a different way of thinking about code.
02 — a different way of reading code

There is no "next line" anymore

When you read normal code, you run a little simulation in your head: this line finishes, then that one starts. It's such a deep habit that it's easy to keep doing it once a second thread enters the picture — and that's exactly where the trouble starts.

Once two threads touch the same piece of memory, a single line like counter += 1 stops being one event. Underneath, it's three: load the current value, add one to it, store it back. Your other thread can slip in and do its own load, add, or store at any point between yours. The scheduler doesn't know or care that you thought of += 1 as a single step.

Below, two threads each want to add 1 to a shared value that starts at 5. Correct math says the end result should be 7. The general rule hiding in this example: any operation that reads a value, computes something from it, and writes it back is only safe from this problem if the read-compute-write happens as one uninterruptible unit — or if you've otherwise guaranteed no one else can touch that value in between. Everything from here on is really just different tools for getting that guarantee.
03 — the basic move

Spawning a thread, and why join isn't optional

thread::spawn takes a closure and hands it to the operating system to run independently. Your main thread doesn't wait for it — it just keeps going, immediately, on its own track.

src/main.rs
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("worker step {i}");
            thread::sleep(Duration::from_millis(50));
        }
    });

    println!("main is already doing its own thing");

    // handle.join() blocks main until the worker closure returns.
    // Skip this call and main might exit — ending the whole
    // process — before the worker ever prints anything.
    handle.join().unwrap();
    println!("worker is done, main can trust that now");
}

The closure passed to spawn owns whatever it captures from the environment — that's what move is for when you see it, and you'll see it constantly, because a spawned thread can outlive the scope it was created in, so it can't safely borrow anything from that scope.

join() is the only thing in this snippet that puts an order back in place: "wait until the worker is finished." Everything else about when the worker's individual print statements happen, relative to main's, is still up for grabs — main and the worker are two separate stories running at once, and join only guarantees where they meet back up, not what happened along the way.

04 — watching it actually break

Rust won't let you write the naive bug — so here's a version it will

If you tried to have two threads directly share a plain &mut i32 and both mutate it, Rust's compiler refuses to build the program at all. That's real, and it's one of the things Rust is genuinely good at: a whole category of this bug is caught before your code ever runs.

But the compiler checks ownership, not timing. If you give both threads shared access through something designed for that — like an atomic value — Rust is satisfied, because each individual read and each individual write is memory-safe. What it can't stop is you doing the read and the write as two separate steps, with a gap in between where another thread can sneak in.

src/main.rs
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::thread;

fn main() {
    let counter = Arc::new(AtomicUsize::new(0));
    let mut handles = vec![];

    for _ in 0..2 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..100_000 {
                let current = counter.load(Ordering::Relaxed);
                counter.store(current + 1, Ordering::Relaxed);
                // load and store are each safe on their own —
                // but nothing stops another thread's load from
                // landing between this load and this store.
            }
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("counter = {}", counter.load(Ordering::Relaxed));
    // expected 200,000 — almost never what you get
}

05 — the fix: forced exclusion

Mutex: only one thread holds the key

A Mutex ("mutual exclusion") wraps a value and adds exactly one rule: to touch what's inside, a thread has to call .lock() and get back a guard. While that guard exists, no other thread's .lock() call can succeed — they simply wait. The load, the modification, and the store all happen while holding that one guard, so there's no gap left for another thread to slip into.

Arc ("atomically reference-counted") is the separate piece that lets multiple threads each own a handle to the same Mutex in the first place. Cloning an Arc doesn't copy the data — it just adds one to a shared counter, and the data itself is freed once that counter hits zero. Think of it as a shared pointer with a built-in headcount, which is exactly what lets several threads legitimately co-own one piece of memory.

src/main.rs
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..2 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..100_000 {
                let mut guard = counter.lock().unwrap();
                *guard += 1;
            } // guard drops here — the lock releases automatically
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("counter = {}", *counter.lock().unwrap());
    // always 200,000, every single run
}

The block between counter.lock().unwrap() and the closing brace is called the critical section — the smallest span of code that genuinely needs exclusive access. A good habit is keeping it as short as possible: lock, do the minimum necessary, let the guard drop. A critical section that holds the lock while doing unrelated slow work (a network call, a big computation) doesn't cause wrong answers, but it does mean every other thread waiting on that lock sits idle for no good reason.

Same bug, opposite fix from section 4: the atomic version there was racy specifically because load and store were two separate operations on the object. A Mutex fixes this by making the entire read-modify-write sequence into one guarded block, rather than by making any single operation itself indivisible.
06 — a different paradigm entirely

Channels: stop sharing, start handing off

Everything so far has been about the same problem: several threads touching the same memory, and needing rules for who touches it when. Channels sidestep the problem instead of solving it — only one thread ever owns the data at any given moment. Others don't reach in and grab it; they receive it, one message at a time.

src/main.rs
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        for n in 1..=5 {
            tx.send(n).unwrap(); // ownership of `n` moves into the channel
        }
    }); // `tx` is dropped here, once the closure ends

    for received in rx {
        println!("got {received}");
    } // the loop ends naturally once every sender has been dropped
}

mpsc stands for multiple producer, single consumer — many threads can hold a clone of tx and send into the same channel, but there's only ever one rx pulling messages out. Each value sent is moved, not shared: once it's sent, the sending thread no longer has it, and the receiving thread is the sole owner from that point on. There's nothing left for two threads to race over, because there's no moment where two threads both have access to the same value.

This is the producer/consumer shape: one or more threads generating work or data, one thread (or a small pool of them) picking it up and processing it in order. It won't save you from every kind of coordination problem — you can still need to know, for instance, that all producers are done before you stop waiting — but it removes the specific "two threads mutate one cell" bug completely, for whatever data flows through it.

07 — waiting for a reason, not a lock

Condvar: sleep until something is actually true

A Mutex answers "only one at a time." It has nothing to say about order. If thread B has to wait until thread A has done something specific first — not just wait for a lock to be free, but wait for a real condition to become true — locking alone doesn't express that. You could make B spin in a loop, repeatedly locking, checking, unlocking, and trying again, but that burns CPU doing nothing thousands of times a second while it waits.

A Condvar gives a thread a way to actually go to sleep — not spin — until another thread wakes it up on purpose.

src/main.rs — the mechanism
use std::sync::{Arc, Mutex, Condvar};
use std::thread;

fn main() {
    let pair = Arc::new((Mutex::new(false), Condvar::new()));
    let pair2 = Arc::clone(&pair);

    thread::spawn(move || {
        let (lock, cvar) = &*pair2;
        let mut ready = lock.lock().unwrap();
        *ready = true;
        cvar.notify_one(); // wake up one thread that's waiting on this cvar
    });

    let (lock, cvar) = &*pair;
    let mut ready = lock.lock().unwrap();
    while !*ready {
        // wait() atomically: unlocks the mutex, sleeps, and re-locks
        // it before returning. The thread holds no lock while asleep.
        ready = cvar.wait(ready).unwrap();
    }
    println!("go!");
}

Notice the Condvar is always paired with a Mutex guarding the actual condition (here, the bool). That's not incidental — wait() needs to release the lock while sleeping (otherwise no one else could ever acquire it to make the condition true), and it needs to reacquire the lock before handing control back to you, so you can safely check the condition again without racing anyone.

The gotcha that matters most: always while, never if. It's tempting to write if !*ready { ready = cvar.wait(ready).unwrap(); } — check once, wait once, assume you're done. Two things break that assumption. First, a thread can wake up from wait() with no one having called notify at all — a "spurious wakeup," which the underlying OS is explicitly allowed to do. Second, when you notify_all(), every waiter wakes up and races to reacquire the lock, but only one condition might actually hold — the rest need to go straight back to sleep. A while loop that rechecks the condition after every wake-up handles both cases correctly. An if handles neither.

Here's that lesson applied to something closer to what you'll actually need: three threads spawned in a random order, but forced to print in a specific order regardless.

src/main.rs — enforcing a strict order
use std::sync::{Arc, Mutex, Condvar};
use std::thread;

struct Turn {
    current: Mutex,
    cvar: Condvar,
}

fn print_in_turn(turn: &Turn, my_turn: u32, label: &str) {
    let mut current = turn.current.lock().unwrap();
    while *current != my_turn {
        current = turn.cvar.wait(current).unwrap();
    }
    println!("{label}");
    *current += 1;
    turn.cvar.notify_all(); // wake everyone — let each recheck whose turn it is
}

fn main() {
    let turn = Arc::new(Turn { current: Mutex::new(0), cvar: Condvar::new() });
    let mut handles = vec![];

    // spawned in a deliberately scrambled order
    for (id, label) in [(2, "third"), (0, "first"), (1, "second")] {
        let turn = Arc::clone(&turn);
        handles.push(thread::spawn(move || print_in_turn(&turn, id, label)));
    }

    for h in handles {
        h.join().unwrap();
    }
    // always prints: first, second, third — regardless of spawn order
    // or which thread the scheduler happens to run first
}

Walk through why this works: every thread immediately tries to lock current and check whether it's their turn. Whoever isn't up yet calls wait() and goes to sleep, lock released. When the thread whose turn it is finishes printing, it increments the counter and calls notify_all() — every sleeping thread wakes up, reacquires the lock one at a time, and rechecks its own condition. Exactly one of them finds it's now their turn; the rest see it still isn't and go straight back to sleep. Nobody needed to know in advance which thread that would be — the while loop figures it out.

This pattern — a shared piece of state describing "whose turn," a Condvar for the waking and sleeping, notify_all because you don't know which specific waiter should wake — covers a large share of the ordering puzzles you'll run into. The names of the threads and what they print will change; the shape underneath usually doesn't.

08 — reading it, and writing it

A method, not a memorized list

The tools above are easy to memorize and easy to reach for at random. What actually transfers to a problem you haven't seen before is a small set of questions you ask before touching a keyboard — whether you're reading someone else's threaded code or writing your own.

01
What's actually shared?
Find the specific variables, fields, or structures more than one thread can touch. Everything else in the code — local variables inside a single thread's closure, data that's moved and never shared again — is not a candidate for any of this and can be set aside.
02
Of that shared state, what's read-only versus mutated?
Multiple threads reading the same immutable value at once is completely fine — an Arc<T> around read-only data needs nothing further. The danger is specifically write access, or a read that's used to decide a write.
03
Is the requirement exclusion, or is it ordering?
"Only one thread touches this at a time" is exclusion — reach for Mutex (or an atomic, for simple counters and flags). "Thread B can't proceed until thread A has done something specific" is ordering — exclusion alone doesn't express that; you need a Condvar, a channel used as a signal, or both.
04
Could this be a hand-off instead of a share?
If the real shape of the problem is "thread A produces something, thread B consumes it," ask whether a channel replaces the shared-state-plus-lock design entirely. It often does, and it's easier to reason about when it does — there's no interleaving to worry about if only one thread ever owns the data.
05
Trace one bad interleaving by hand.
Pick a specific, deliberately unfriendly order — two threads' critical sections starting at the same instant, a notify firing before the corresponding wait, a sender finishing before a receiver is even created. Walk the code through that exact order, line by line. If it still ends up correct, that's real evidence, not just a passing test run.

None of this replaces understanding the primitives. But most of the difficulty in this space isn't "which function do I call" — it's noticing, up front, which of these five questions the problem in front of you is actually asking.

09 — quick reference

Four tools, four shapes of problem

Almost every synchronization puzzle you'll meet is one of these shapes, or a combination of two of them.

Mutex + Arc
Several threads need to mutate the same piece of state. Lock, mutate, let the guard drop. Keep the critical section as small as it can be.
shape: shared mutable state
Channel (mpsc)
One or more threads produce values, one thread consumes them. Ownership transfers with each send — nothing is ever touched by two threads at once.
shape: hand-off, produce/consume
Condvar
A thread must wait, without spinning, until a specific condition becomes true — not just until a lock is free. Always recheck the condition in a while, never an if.
shape: ordering, signaling
Atomic types
For a single counter or flag, an AtomicUsize or AtomicBool can skip the overhead of a full Mutex — but remember: only individual operations like fetch_add are indivisible. Separate load then store calls are not, as section 4 showed.
shape: simple shared counters/flags

The shape rarely announces itself in the problem statement. Finding it — is this really exclusion, or is it secretly ordering; is this really shared state, or is it secretly a hand-off — is most of the actual work.
