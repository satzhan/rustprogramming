Sharing to Write
Arc, Mutex, and the cost of a door

Threads that only read can share almost for free. Threads that write need an arrangement, and every arrangement has a price. This guide is about choosing the cheapest arrangement that is still correct, and recognizing the many cases where the answer is no lock at all.

section 1

Memory is shared by default

Start below the language. The operating system builds one wall, and it builds it between processes: each process gets its own address space, its own page tables, its own view of memory. One process cannot reach another's bytes without asking the kernel.

Threads live on the other side of that design. All threads of a process share one address space. Every thread can already reach every byte the process owns: the same heap, the same globals, the same everything. The hardware raises no objection when two threads write the same address in the same nanosecond.

address spaces: the wall the OS builds, and where it does not

So "can threads share data" is never the question. The machine says yes before anyone asks. The real question is what discipline governs the sharing, because unrestricted simultaneous access to the same bytes produces answers that depend on nanosecond timing.

Rust's contribution is not sharing. Sharing is the default condition of the hardware. Rust's contribution is refusal: a set of compile-time rules that reject programs whose correctness would depend on timing. Everything in this guide is one of the machine's permissive defaults meeting one of those refusals, and the escape hatch the standard library provides.

section 2

Reading is free, writing is the wall

Rust compresses all of its sharing discipline into one rule, and the rule is worth memorizing in exactly this form:

any number of readers, or exactly one writer. never both.

The rule is sometimes written aliasing XOR mutation: many names for the same data, or the power to change it, never both at once. It is enforced on references at compile time, before the program exists.

the rule, as a machine: set each thread's intent

Click a cell to cycle idle → read → write. The verdict follows the one rule above.

Where does Arc sit in this? Arc<T> manufactures aliasing on purpose: many owners, on many threads, of one value. Because aliasing is its whole job, Arc will hand out &T freely and &mut T essentially never. Ten threads holding an Arc<Vec<i32>> can all read the vector at once. None of them can push to it. The compiler is not being cautious; it is applying the rule literally. Ten aliases exist, so mutation is off the table.

// ten threads may hold this at once, and all may read.
let readings: Arc<Vec<i32>> = Arc::new(load());

// but this line does not compile from inside a thread:
readings.push(42);   // error: cannot borrow as mutable

This is not a limitation to route around. It is half of the design. The read-only case is the good case, and the machine agrees:

standard architecture fact Under the cache-coherence protocols in mainstream CPUs, a cache line being read by many cores can sit in every core's cache simultaneously, in a shared state. The moment one core writes that line, every other core's copy is invalidated and must be re-fetched. Read-only data parallelizes at the hardware level; written data is dragged from core to core.

So when the work genuinely needs no writes to shared state, Arc alone finishes the story. The rest of this guide exists for the other case: the threads have something to say, a total to add, a table to update, a result to record. For that, the rule must be enforced at runtime instead of compile time, one thread at a time. That runtime enforcer is the mutex.

section 3

Mutex anatomy: what a lock physically is

Strip the abstraction. A mutex is a word of memory, one machine word holding a state like unlocked or locked, placed next to the data it protects. Locking is an atomic compare-exchange on that word: "if you are unlocked, become locked, and tell me whether I won." One indivisible hardware operation.

The price depends entirely on whether anyone else is at the door.

  • Uncontended: the compare-exchange succeeds on the first try. No kernel, no waiting. Cost on the order of nanoseconds, comparable to a handful of arithmetic instructions.
  • Contended: the word says locked. The thread typically spins briefly, then asks the OS to put it to sleep until the holder releases (on Linux this is the futex mechanism). Sleeping and waking a thread costs on the order of microseconds, thousands of times the uncontended path. And the cache line holding the lock word starts ping-ponging between cores, each transfer costing far more than the arithmetic it guards.
verified in rust In Rust the mutex owns its data: Mutex<T> wraps the value inside itself, and lock() returns a guard, the only path to the data. There is no way to reach T while forgetting to lock, because the door is the only entrance. This differs from C and C++, where a mutex and the data it protects are related only by programmer discipline. The .unwrap() after lock() handles poisoning: if a thread panics while holding the lock, the mutex is marked poisoned so other threads learn the protected data may be half-updated.
let tally = Arc::new(Mutex::new(0));
// ... inside a thread:
let mut guard = tally.lock().unwrap();  // wait here if occupied
*guard += partial;                          // exclusive access
// guard dropped: door reopens

The deeper cost is not the lock operation itself. It is what the lock does to the shape of the program: everything between lock and unlock runs one thread at a time. That region is serial code wearing a concurrent costume. And there is a hard ceiling on what serial code allows, no matter how many cores arrive to help:

the serial ceiling

The dashed line is the ceiling: with a fraction f of the work serialized behind the lock, speedup can never exceed 1 / f, no matter the core count.

illustrative model The curve plots the classic serial-fraction formula (speedup = 1 / (f + (1 − f) / N)), not a live measurement. Real programs bend further below it: cache-line transfers, wake-up latency, and memory bandwidth all push down. Treat the ceiling as optimistic, which makes the argument stronger, not weaker.

Read the widget backwards and it becomes design advice. The lever that matters is not the thread slider. It is the lock slider: shrinking the fraction of work behind the door raises the ceiling for every core count at once. Which raises the practical question of the next section: what decides that fraction?

section 4

Holding the door: the guard's lifetime is a dial

In Rust nothing unlocks a mutex explicitly. The guard returned by lock() unlocks it when the guard is dropped, at the end of its scope, or earlier if dropped by hand:

let mut guard = shared.lock().unwrap();
update(&mut guard, value);
drop(guard);            // door reopens here, not at the closing brace
// ... expensive local work continues, unlocked

That drop is not ceremony. The serialized region of the program is exactly the guard's lifetime, so the placement of that one line decides how much of each iteration runs one-at-a-time. Most accidental serialization in real code is nothing more exotic than a guard held a few lines too long, usually across formatting, I/O, or allocation that never needed protection.

drag the release point, watch two threads breathe or suffocate

Each iteration has five steps. Only step 3 touches shared state. Choose where the guard drops:

Solid red outline = holding the lock. Dashed = waiting for it. Two iterations per thread.

The discipline that falls out: lock late, release early, and let nothing live inside the critical section except the touch of shared state itself. Compute before the door. Format and print after it. The guard is a scalpel, not a blanket.

judgment A useful review habit: read every critical section and ask of each line, "does this line need the other threads stopped?" Any line answering no is a candidate to move out. This is craft, not a compiler rule; the borrow checker is indifferent to how long a guard lives, so scope hygiene is on the programmer.
section 5

Two philosophies: shared clipboard vs private notebooks

Now the central design fork. Suppose N threads each process a slice of the work, and each produces contributions that must combine into one final answer, a total, a maximum, a top-k table. There are exactly two shapes for where the combining happens.

Philosophy 1: the shared clipboard

One structure, wrapped in Arc<Mutex<...>>, and every thread walks to it for every contribution. The final answer is always sitting there, current as of the last unlock.

let best = Arc::new(Mutex::new([0; 3]));   // shared clipboard
// each thread, for each group it processes:
let mut guard = best.lock().unwrap();
insert_top3(&mut guard, total);
drop(guard);

Philosophy 2: private notebooks

Each thread keeps its own local structure, plain stack data, no wrapper, no lock. Combining happens once, after join, in the parent. The thread's return value rides back through its JoinHandle.

let handle = thread::spawn(move || {
    let mut local = [0; 3];        // private notebook
    // ... insert_top3(&mut local, total) for each group ...
    local                            // returned through the handle
});
// parent, after all joins: merge N notebooks, N small steps, zero locks

Both philosophies produce the identical answer. The clipboard takes the lock once per contribution, 48 times here, thousands of times on real input. The notebooks take it zero times, and pay instead with N merge steps at the very end, four small function calls. When the combining operation can be deferred, the notebook wins so decisively that the honest summary is:

the cheapest lock is the one never taken. before reaching for Arc<Mutex>, ask whether the sharing can be designed away.

judgment The notebook trick requires the combine step to tolerate postponement: sums, counts, maxima, top-k tables all merge cleanly after the fact. The clipboard becomes the right call when postponement breaks the problem: when the program needs the live value mid-flight (a progress display another thread reads), when threads must react to the global state as it evolves (stop early once a target is found, feed a shared cache whose entries later work reuses), or when per-thread copies would be too large to hold N times. "Arc plus Mutex is often avoidable" and "Arc plus Mutex is sometimes exactly right" are both true; the skill is telling the cases apart, which section 8 turns into practice.
section 6

Dividing the work: stripes, blocks, and silent arithmetic bugs

Both philosophies begin the same way: the input must be split across threads. Two standard partitions exist, and both are pure index arithmetic.

  • Interleaved (striding): worker id takes items id, id + N, id + 2N, ... Every worker starts at its own id and steps by the worker count. No chunk-size math, no slicing, and the leftover items when the count does not divide evenly distribute themselves.
  • Blocks (chunking): worker id takes one contiguous range. Requires ceiling division for the chunk size (len.div_ceil(n)), and the last chunk runs shorter.
// interleaved: the whole partition is two lines
let mut i = id;
while i < items.len() {
    // ... process items[i] ...
    i += num_threads;      // the stride MUST equal the worker count
}
24 items, colored by owner. break the arithmetic and watch what the compiler cannot see

In interleaved mode the stride and the worker count are separate sliders on purpose. They should never disagree; move them apart to see why.

The failure modes deserve names, because the compiler catches neither. This is arithmetic, not aliasing, and the borrow checker is blind to it:

  • Stride > workers: orphans. Some items are visited by nobody. The program runs cleanly, joins cleanly, and returns a confidently wrong answer.
  • Stride < workers: duplicates. Two workers walk the same residue class and some items are counted twice.
worth staring at Whether duplicates are fatal depends on the algebra of the combine step. A maximum shrugs off double visits: max(x, x) = x, the operation is idempotent. A sum does not: counting an item twice changes the answer. Orphans are fatal to everything. So the same partition bug can be invisible in one program and catastrophic in its neighbor, which is exactly why it survives testing.
judgment On cache behavior: contiguous blocks stream through memory in order, which prefetchers love; interleaving makes each worker hop by N elements. For an array of small elements this can matter; for this guide's shape of work, where each item is itself a heap-allocated group, both partitions chase pointers anyway and the difference is likely noise. Correct arithmetic first, locality second, and measure before believing either claim about speed.
section 7

The counter shortcut: when the data is one word

One special case is common enough to earn its own tool. When the shared state is a single machine word, a counter, a flag, an id dispenser, wrapping it in a mutex means building a door to guard one coin. The hardware offers something smaller: atomic operations, single instructions that read-modify-write one word indivisibly.

one increment, two prices

Mutex<i64>

  • compare-exchange the lock word
  • read the value
  • write value + 1
  • store unlocked, maybe wake a sleeper
0

AtomicI64

  • fetch_add: one indivisible instruction
0

Both are correct. One is a door with a protocol; the other is the coin defending itself.

use std::sync::atomic::{AtomicI64, Ordering};

let count = Arc::new(AtomicI64::new(0));
// any thread, no guard, no unwrap, cannot be held too long:
count.fetch_add(1, Ordering::Relaxed);

Honest scope: atomics operate on one word at a time. A compound structure, say a three-slot leaderboard where inserting a value shifts two others, cannot be one atomic operation, because it is three dependent writes and the hardware guarantees indivisibility for one. Between two of those writes, another thread could observe the table mid-shift. Multi-word invariants are mutex territory (or notebook territory). Techniques exist to build lock-free structures from compare-exchange loops; they are real, they are hard, and they are beyond this course.

closing the loop The A in Arc stands for atomic, and it is exactly this machinery. Arc's reference count is an atomic integer: clone is a fetch_add, dropping is a fetch_sub, and the thread whose decrement reaches zero frees the value. The tool this course has been leaning on since threads began is built from the primitive on this page.
section 8

The decision landscape

The full menu, cheapest discipline first. Every row is correct somewhere; cost rises going down, so the craft is stopping at the first row that fits.

  • Move it: one thread needs it, ownership transfers, nothing is shared.
  • Scoped borrow (thread::scope): threads provably end before the owner; plain & references work.
  • Clone it: the data is small; independent copies are cheaper than any coordination.
  • Channel: values flow one way between threads; transfer, not sharing.
  • Arc: many long-lived threads read one large value; nobody writes.
  • Arc<Atomic>: shared writes, but the state is one word.
  • Arc<Mutex>: shared writes to compound state that genuinely cannot wait for a merge.

A last calibration. Nothing on this page makes a program faster by itself; threads are a bet that coordination costs less than the work saved, and the bet must be checked with a stopwatch on real input, in release mode. What this page gives is the other half: the discipline that keeps the fast program correct, and the eye for the many designs where the discipline costs nothing because the sharing was never necessary.
