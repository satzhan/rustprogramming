Arc: who turns off
the lights?

A tour of one type with one job. Arc answers a single question: when several threads hold the same data and any of them might finish last, who frees it? Everything else here, cloning, scoping, locking, is either a way to dodge that question or a consequence of answering it.

the running example

A server left behind readings.txt: one latency measurement per line, about a million lines. Somewhere in it is the worst request it ever served. Finding a maximum is trivial. Finding it on all cores at once is where ownership gets interesting.

A surface reading of this ladder says "some versions compile and some do not," and that reading cannot explain why rung four fails when rung three passed: the code barely changed. The ledger can. What changed is where the proof lives. Rung three proves the lifetime at compile time with a closing brace. Rung four has no brace that fences the workers, so no proof can exist in the source. Arc moves the proof into the running program: sixteen bytes of counter that get checked at runtime instead of a fact checked before the program exists.

02

What an Arc physically is

Not a wrapper, not magic: a pointer on each stack, and a small ledger stapled to the front of one heap allocation. Toggle the two worlds, then hover or tap the header block.

verified against the compiler

Arc::clone(&x) copies eight bytes (the pointer) and atomically increments one counter. The data itself is not touched. The programs in section 04 print this bill at runtime; nothing here is asserted from memory.

implementation detail, not a guarantee

In the current standard library the heap block begins with two AtomicUsize counters, strong and weak, sixteen bytes on a 64-bit target, followed by your data. The counts are observable through Arc::strong_count; the exact layout is the library's business and could change.

The comparison that makes Arc make sense

A garbage-collected runtime gives every object this treatment, invisibly and always. References are shared freely, the bookkeeping is hidden, and the moment of freeing is unknowable: it happens when the collector wakes up, on its schedule, not yours. That is a fine trade for many programs. It is a bad trade when you care where data lives and when it dies.

Rust inverts the default. Nothing is counted unless you say so, which is why sharing requires you to type the word Arc. The ledger exists only where you asked for it, its cost is visible in the type, and the free is deterministic: the instant the count reaches zero, on that exact line, on whichever thread happened to leave last. The surface story is "Arc lets you share." The machine story is "Arc is sixteen bytes of bookkeeping you opted into, and clone is one atomic increment."

03

The headcount, live

strong_count is not a metaphor. It is an integer, and it can be watched. Check workers in, join them back out, and see when the data actually dies.

verified against the compiler

With the switch on, a real run prints counts 1, 4, 3, 2, 1 as three workers arrive and leave. With it off, the same program prints 1 the whole way down: a move closure captures only variables its body uses, so an untouched clone drops on the spot, before the thread even runs. This trap was found by falling into it, not by reading about it.

the line that forces the capture
let data = Arc::clone(&data);
handles.push(thread::spawn(move || {
    thread::sleep(Duration::from_millis(50 * (id + 1)));
    data.len() // delete this line and the clone is never captured at all
}));
04

The bill meter

Sharing by clone and sharing by Arc both compile. Only one of them scales. Drag the sliders; the bars are log scale because the ratio is the point.

readings in the log: 1,000,000
threads: 4
judgment · measure before trusting

The copy bill above is arithmetic and exact. What it buys is not: for a pure scan of a contiguous array, memory bandwidth is usually the ceiling, so four threads rarely mean four times faster. The clone version pays twice, once streaming the copies through the bus and again in cache pressure as four private copies compete for the same cache. How much twice costs depends on the machine. The programs behind this page print their own timings when run; the numbers belong to whatever laptop runs them, not to this page.

05

Writing through the shared door

Arc solved exactly one problem: who frees the data. Ask it to solve a different one, who may write and when, and it refuses in plain text.

the wish: every worker pushes its chunk peak into one shared vector
let peaks = Arc::new(Vec::<u64>::new());
// ... inside each worker:
peaks.push(m); // write through an Arc?
the verdict, verbatim
error[E0596]: cannot borrow data in an `Arc` as mutable
   = help: trait `DerefMut` is required to modify through a dereference,
     but it is not implemented for `Arc<Vec<u64>>`

Several writers pushing into one vector with no rule about turns is a data race, and the type system declines to be a party to it. The rule about turns is a second type with a second job: Mutex. Arc shares the door, Mutex is the lock on it, and the guard is a key held briefly and returned automatically. But a lock is not free. It makes threads take turns, and turns are a queue.
