Building a FIFO dispatcher in Rust

A program receives jobs. Some jobs take longer than others. Several workers can run jobs at the same time, but there are limits to how much work the machine should accept. Who decides what runs next?

We'll begin with one queue and one worker. Every new piece of Rust will solve a problem that appears along the way.

Run the examples: Open a Rust project in Codespaces or on your computer. Replace src/main.rs with an example and run cargo run. Each complete example uses only the Rust standard library. The diagrams and controls on this page work without internet access.
Jobs arrive→Queue→Manager→Workers
1 · One worker

A queue decides the order

Imagine three jobs arriving in this order: A, B, C. The rule is simple: take A first. If a new job D arrives while A is running, D goes behind C. That is first in, first out (FIFO).

VecDeque lets us add an item at the back and remove an item from the front. A Vec can remove its first item too, but that operation shifts the remaining elements; VecDeque is built for this use.

Move the queue yourself

The outlined job is next. Taking a job removes it from the queue; finishing the job is a separate event.

A is at the front.
1. FIFO, without threads
use std::collections::VecDeque;

fn main() {
    let mut queue = VecDeque::new();
    queue.push_back("A");
    queue.push_back("B");
    queue.push_back("C");

    while let Some(job) = queue.pop_front() {
        println!("Starting {job}");
    }
}
Copy into src/main.rs and run cargo run.
What does while let Some(job) mean?

pop_front() returns Some(job) when it finds an item and None when the queue is empty. The loop keeps running while it gets an item. No index is needed.

Change itReplace push_back("C") with push_front("C"). Run it. You haven't changed the worker at all. Only the rule for entering the queue has changed.

Now make processing take time. While A is running, B and C wait. Could another worker help?

2 · More than one worker

Waiting and working are not the same

Suppose a job waits for a response from a disk or a network connection. While it waits, another job could make progress. With one thread, our program processes the jobs in a row. Multiple threads can overlap the waiting.

The next program starts four threads. It isn't a worker pool yet: it creates one thread per job. That is enough to see what changes.

2. Four jobs on separate threads
use std::thread;
use std::time::{Duration, Instant};

fn main() {
    let start = Instant::now();
    let mut handles = Vec::new();

    for id in 0..4 {
        handles.push(thread::spawn(move || {
            println!("Job {id} starts");
            thread::sleep(Duration::from_millis(300));
            println!("Job {id} ends");
        }));
    }

    for handle in handles {
        handle.join().unwrap();
    }
    println!("Elapsed: {:?}", start.elapsed());
}
Copy into src/main.rs and run cargo run.

spawn asks the operating system to run a new thread. join waits for that thread to finish. Without the joins, main could end before the others have completed. The order of printed lines can change between runs.

How many workers?

Six equally long waiting jobs. Each colored block is one job; the horizontal width represents elapsed time. This is a scheduling model, not a benchmark.

Change itRun the program once. Then replace the spawned threads with one ordinary for loop that prints, sleeps, and prints. Compare elapsed times. Finally try doing calculation instead of sleeping. That comparison is different: CPU work needs actual processor time.
A sleep tells the operating system that this thread does not need to run until later. It does not burn CPU for that duration. Parallel CPU computation behaves differently from overlapping waits.
3 · Sharing jobs

Two workers, one queue

Creating one thread per job becomes awkward when jobs keep arriving. Instead, keep a fixed number of workers and let each one take the next job from a shared queue.

Now we have a problem: two workers might try to take the same next job at once. The queue must have one moment when a worker takes an item and everyone else stays out.

Mutex provides that exclusive access. Arc lets multiple threads own handles to the same queue. They do different jobs: Arc shares ownership; Mutex protects mutation.

3. Two threads share one FIFO queue
use std::collections::VecDeque;
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

fn main() {
    let queue = Arc::new(Mutex::new(VecDeque::from([
        300u64, 100, 200, 400,
    ])));
    let mut handles = Vec::new();

    for worker in 0..2 {
        let queue = Arc::clone(&queue);
        handles.push(thread::spawn(move || loop {
            let job = {
                let mut q = queue.lock().unwrap();
                q.pop_front()
            }; // lock released here

            match job {
                Some(ms) => {
                    println!("Worker {worker} took {ms} ms job");
                    thread::sleep(Duration::from_millis(ms));
                }
                None => break,
            }
        }));
    }

    for h in handles {
        h.join().unwrap();
    }
}
Copy into src/main.rs and run cargo run.

Look at the small inner block around pop_front(). The lock is held only while taking a job. The worker releases it before spending time on the job. Another worker can then take the next job.

Why does Arc::clone(&queue) not copy the queue?

It creates another owning handle pointing to the same allocation. Arc keeps a thread-safe count of owners. The queue remains one shared queue.

Who unlocks the mutex?

The value returned by lock() is a guard. When q leaves its scope, that guard is dropped and the mutex unlocks. You can also call drop(q) explicitly.

How long should the lock be held?

Four jobs, two workers. Each job takes one time unit. Compare locking only while taking a job with locking throughout the job.

Change itIn example 3, move thread::sleep(...) inside the block holding q. You will need to reorganize the loop. Watch what happens when one worker holds the lock while working. Then put the sleep back outside the lock.

There is still a problem. Our workers stop when the queue is empty. What if a new job arrives a moment later?

4 · Jobs arrive later

Wait without repeatedly asking

When a queue is empty, a worker has three choices: leave, keep checking, or wait until someone signals that something changed. Leaving misses future jobs. Checking over and over wastes time. A Condvar lets the worker sleep until it is notified.

The important part is easy to miss: waiting on a condition variable temporarily releases the mutex. Otherwise the producer could not get the lock to add a job.

Follow the empty queue

    4. A producer wakes a waiting consumer
    use std::collections::VecDeque;
use std::sync::{Arc, Condvar, Mutex};
use std::thread;
use std::time::Duration;

struct State {
    jobs: VecDeque<u32>,
    closed: bool,
}

fn main() {
    let shared = Arc::new((
        Mutex::new(State {
            jobs: VecDeque::new(),
            closed: false,
        }),
        Condvar::new(),
    ));

    let consumer_shared = Arc::clone(&shared);
    let consumer = thread::spawn(move || loop {
        let job = {
            let (lock, ready) = &*consumer_shared;
            let mut state = lock.lock().unwrap();
            while state.jobs.is_empty() && !state.closed {
                state = ready.wait(state).unwrap();
            }
            state.jobs.pop_front()
        };
        match job {
            Some(n) => println!("Processing job {n}"),
            None => break, // queue closed and empty
        }
    });

    thread::sleep(Duration::from_millis(200));
    for n in 1..=3 {
        let (lock, ready) = &*shared;
        {
            let mut state = lock.lock().unwrap();
            state.jobs.push_back(n);
        }
        ready.notify_one();
        thread::sleep(Duration::from_millis(100));
    }
    let (lock, ready) = &*shared;
    lock.lock().unwrap().closed = true;
    ready.notify_all();
    consumer.join().unwrap();
}
    Copy into src/main.rs and run cargo run.

    The worker waits in a while loop, not an if. A notification only means it should check again; it is not a promise that a job is available. Another worker may have taken the job first, or a thread can wake without a notification.

    The closed flag is necessary too. An empty queue means “nothing here now.” A closed and empty queue means “nothing else will arrive.” Without that distinction, workers can wait forever at shutdown.

    Change itDelete ready.notify_one() after adding a job and run the example. The worker might eventually wake during shutdown, but it no longer responds when jobs arrive. Put the notification back.
    5 · One thread makes decisions

    The manager hands work to workers

    So far each worker chooses its own job. But suppose we need one place to decide whether a job is allowed to start. We can introduce a manager.

    The manager takes the next waiting job, makes a decision, and sends it to a worker. A channel is a way to hand a value from one thread to another. The value moves through the channel; the receiver takes ownership of it.

    Producer→Waiting queue→Manager→Channel→Workers
    5. Send jobs over a channel
    use std::sync::{mpsc, Arc, Mutex};
use std::thread;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel::<u32>();
    let shared_rx = Arc::new(Mutex::new(rx));
    let mut handles = Vec::new();

    for worker in 0..2 {
        let rx = Arc::clone(&shared_rx);
        handles.push(thread::spawn(move || loop {
            let next = {
                let receiver = rx.lock().unwrap();
                receiver.recv()
            };
            let Ok(job) = next else { break };
            println!("Worker {worker} runs job {job}");
            thread::sleep(Duration::from_millis(150));
        }));
    }

    for job in 1..=6 {
        tx.send(job).unwrap();
    }
    drop(tx); // tell receivers no more values will arrive

    for h in handles {
        h.join().unwrap();
    }
}
    Copy into src/main.rs and run cargo run.

    Rust's standard mpsc channel has one receiving end. We use Arc<Mutex<Receiver<u32>>> to let workers share that receiver. Only one worker can be inside recv() at a time, and a blocking recv() holds the receiver mutex. Once a worker receives a job, it releases the lock and processes the job independently.

    That arrangement can work, but it is a choice with a cost. A channel also holds sent jobs internally. A job can have been sent but not yet started.

    Why is drop(tx) important?

    recv() returns an error when every sender has been dropped and the channel is empty. If a sender is still alive, a worker cannot distinguish “more jobs might arrive” from “we are finished.” It can keep waiting.

    6 · A limit on running work

    The oldest job may not fit

    Imagine the machine has a budget of 70 units. One running task is using 40. Another worker is free. The next waiting task asks for 40 units, but only 30 remain.

    The manager must wait if it follows strict FIFO. A smaller job behind the first one could fit, but strict FIFO does not look past the front. This is called head-of-line blocking.

    Dispatch under a resource limit

    The number called “CPU budget” here is a reservation limit made by the program. It is not a measurement of actual hardware utilization.

    Capacity: 70. One worker has the existing job; one is free.

    Running / reserved

    Waiting in the queue

    Choose a policy, then dispatch.
    Waiting jobs: A needs 40; B needs 20; C needs 10. With strict FIFO, the manager cannot skip a blocked front job.

    The real difficulty is not the subtraction. It is making the decision safely when several threads can change the counters. Checking the budget and reserving it must happen while holding the same lock. Otherwise two decisions could both see room for one job and both take it.

    6. Resource reservations, without FIFO yet
    use std::sync::{Arc, Condvar, Mutex};
use std::thread;
use std::time::Duration;

#[derive(Default)]
struct Usage { cpu: u32, workers: usize }

struct Budget {
    usage: Mutex<Usage>,
    changed: Condvar,
}

impl Budget {
    fn reserve(&self, cost: u32) {
        let mut u = self.usage.lock().unwrap();
        while u.cpu + cost > 70 || u.workers == 2 {
            u = self.changed.wait(u).unwrap();
        }
        u.cpu += cost;
        u.workers += 1;
    }

    fn release(&self, cost: u32) {
        let mut u = self.usage.lock().unwrap();
        u.cpu -= cost;
        u.workers -= 1;
        drop(u);
        self.changed.notify_all();
    }
}

fn main() {
    let budget = Arc::new(Budget {
        usage: Mutex::new(Usage::default()),
        changed: Condvar::new(),
    });
    let mut handles = Vec::new();

    for (id, cost) in [40u32, 40, 20, 10].into_iter().enumerate() {
        let budget = Arc::clone(&budget);
        handles.push(thread::spawn(move || {
            budget.reserve(cost);
            println!("Job {id} reserved {cost}");
            thread::sleep(Duration::from_millis(250));
            budget.release(cost);
        }));
    }
    for h in handles { h.join().unwrap(); }
}
    Copy into src/main.rs and run cargo run.

    This example protects two counters together: reserved CPU units and reserved worker slots. Notice what it does not guarantee: the threads race to reserve their budgets, so their reservation order is not necessarily FIFO. A single manager will supply that ordering later.

    Why is the resource reservation inside the mutex?

    Suppose two threads each observe 30 units free and each wants 20. If the check happens outside the lock, both can decide they fit. The combined reservation is 40, which exceeds the 30 available. Locking the check and update as one operation prevents this.

    Change itChange the worker limit from 2 to 1. Then change the CPU limit from 70 to 50 in both places inside reserve. Compare which limit prevents overlap. Keep every job cost at or below the capacity; otherwise a job that can never fit will wait forever.
    7 · See what happened

    One number cannot tell the whole story

    Suppose a job arrives at time 2, starts at time 5, and ends at time 9. It waited for 3 time units, ran for 4, and spent 7 in the system altogether. These are different things worth measuring.

    Move a job through time

    Waiting3
    Running4
    Turnaround7
    Waiting = start − arrival; turnaround = finish − arrival.

    For many jobs, we can record each arrival, start, and finish time, then calculate averages. A monitor can also sample system state at regular intervals and write rows to a CSV file.

    MeasurementWhat it answers
    Wait timeHow long between arrival and actual start?
    TurnaroundHow long from arrival to completion?
    Queue lengthHow many jobs remain in the waiting queue?
    Worker slots reservedHow much capacity has the manager booked?
    CPU budget reservedHow much of the program's allowed budget is booked?
    MakespanHow long until the final job completes?
    Be precise about what a counter means. A booked worker slot is not necessarily a thread actively executing a job. The manager can reserve a slot before a worker receives the job. Also, if the manager has already removed the head job from the queue while waiting for capacity, that job will not appear in the queue-length count.

    We should also distinguish FIFO dispatch order from FIFO completion order. If A takes 800 ms and B takes 100 ms, B can finish first even when A was sent first.

    8 · All the parts together

    A small dispatcher

    Here is the whole arrangement. The generator adds jobs to a queue. The manager takes them in FIFO order and waits for capacity. Workers receive the admitted jobs through a channel. Another thread samples how the system is doing.

    There are two separate reasons a job might wait: it may still be in the manager's queue, or the manager may have taken it from that queue but be waiting to reserve capacity. Keeping those states separate is important when reading the measurements.

    Open the full Rust program

    One complete file, using only the standard library. It writes fifo.csv to the working directory. The jobs use sleep to stand in for work; the CPU budget is an accounting rule, not real hardware use.

    8. Generator → FIFO manager → workers → CSV
    use std::collections::VecDeque;
use std::fs::File;
use std::io::Write;
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::{mpsc, Arc, Condvar, Mutex};
use std::thread;
use std::time::{Duration, Instant};

#[derive(Clone, Copy)]
struct Job {
    id: usize,
    cost: u32,
    duration_ms: u64,
    arrival: Instant,
}

struct QueueState {
    jobs: VecDeque<Job>,
    closed: bool,
}
struct Queue {
    state: Mutex<QueueState>,
    available: Condvar,
}
impl Queue {
    fn new() -> Self {
        Self {
            state: Mutex::new(QueueState {
                jobs: VecDeque::new(), closed: false,
            }),
            available: Condvar::new(),
        }
    }
    fn add(&self, job: Job) {
        self.state.lock().unwrap().jobs.push_back(job);
        self.available.notify_one();
    }
    fn next(&self) -> Option<Job> {
        let mut s = self.state.lock().unwrap();
        while s.jobs.is_empty() && !s.closed {
            s = self.available.wait(s).unwrap();
        }
        s.jobs.pop_front()
    }
    fn close(&self) {
        self.state.lock().unwrap().closed = true;
        self.available.notify_all();
    }
    fn len(&self) -> usize {
        self.state.lock().unwrap().jobs.len()
    }
}

#[derive(Default)]
struct UseCount { cpu: u32, slots: usize }
struct Budget {
    state: Mutex<UseCount>,
    changed: Condvar,
    cap: u32,
    max_workers: usize,
}
impl Budget {
    fn reserve(&self, cost: u32) {
        assert!(cost <= self.cap);
        let mut s = self.state.lock().unwrap();
        while s.cpu + cost > self.cap || s.slots >= self.max_workers {
            s = self.changed.wait(s).unwrap();
        }
        s.cpu += cost;
        s.slots += 1;
    }
    fn release(&self, cost: u32) {
        let mut s = self.state.lock().unwrap();
        s.cpu -= cost;
        s.slots -= 1;
        drop(s);
        self.changed.notify_all();
    }
    fn snapshot(&self) -> (u32, usize) {
        let s = self.state.lock().unwrap();
        (s.cpu, s.slots)
    }
}

struct ResultRow { wait_ms: u128, turn_ms: u128 }

fn main() {
    let start = Instant::now();
    let queue = Arc::new(Queue::new());
    let budget = Arc::new(Budget {
        state: Mutex::new(UseCount::default()),
        changed: Condvar::new(), cap: 70, max_workers: 3,
    });
    let results = Arc::new(Mutex::new(Vec::<ResultRow>::new()));
    let finished = Arc::new(AtomicBool::new(false));

    let (tx, rx) = mpsc::channel::<Job>();
    let rx = Arc::new(Mutex::new(rx));

    let mut workers = Vec::new();
    for worker_id in 0..3 {
        let rx = Arc::clone(&rx);
        let budget = Arc::clone(&budget);
        let results = Arc::clone(&results);
        workers.push(thread::spawn(move || loop {
            let task = { rx.lock().unwrap().recv() };
            let Ok(job) = task else { break };
            let began = Instant::now();
            println!("Worker {worker_id}: job {}", job.id);
            thread::sleep(Duration::from_millis(job.duration_ms));
            let ended = Instant::now();
            results.lock().unwrap().push(ResultRow {
                wait_ms: began.duration_since(job.arrival).as_millis(),
                turn_ms: ended.duration_since(job.arrival).as_millis(),
            });
            budget.release(job.cost);
        }));
    }

    let monitor_queue = Arc::clone(&queue);
    let monitor_budget = Arc::clone(&budget);
    let monitor_finished = Arc::clone(&finished);
    let monitor = thread::spawn(move || {
        let mut csv = File::create("fifo.csv").unwrap();
        writeln!(csv, "elapsed_ms,queue,reserved_cpu,reserved_slots").unwrap();
        while !monitor_finished.load(Ordering::Relaxed) {
            let (cpu, slots) = monitor_budget.snapshot();
            writeln!(csv, "{},{},{},{}",
                start.elapsed().as_millis(),
                monitor_queue.len(), cpu, slots).unwrap();
            thread::sleep(Duration::from_millis(100));
        }
    });

    let manager_queue = Arc::clone(&queue);
    let manager_budget = Arc::clone(&budget);
    let manager = thread::spawn(move || {
        while let Some(job) = manager_queue.next() {
            manager_budget.reserve(job.cost);
            tx.send(job).unwrap();
        }
        // tx is dropped when this thread ends
    });

    let generator_queue = Arc::clone(&queue);
    let generator = thread::spawn(move || {
        for id in 0..12 {
            let cost = if id % 3 == 0 { 40 } else { 10 };
            generator_queue.add(Job {
                id, cost, duration_ms: 300,
                arrival: Instant::now(),
            });
            thread::sleep(Duration::from_millis(70));
        }
        generator_queue.close();
    });

    generator.join().unwrap();
    manager.join().unwrap();
    for h in workers { h.join().unwrap(); }
    finished.store(true, Ordering::Relaxed);
    monitor.join().unwrap();

    let results = results.lock().unwrap();
    let n = results.len() as u128;
    let wait: u128 = results.iter().map(|r| r.wait_ms).sum();
    let turn: u128 = results.iter().map(|r| r.turn_ms).sum();
    println!("Completed: {}", results.len());
    if n > 0 {
        println!("Average wait: {} ms", wait / n);
        println!("Average turnaround: {} ms", turn / n);
    }
    println!("Total elapsed: {:?}", start.elapsed());
    println!("Samples written to fifo.csv");
}

    Notice the shutdown order. The generator closes the queue; the manager drains it and then drops its sender; the workers finish their jobs and exit; finally the monitor stops. If you change who holds a sender or who waits for whom, shutdown can become a problem even when ordinary job processing works.

    After the walkthrough

    Change the system and watch what moves

    Start with the complete program. Change one thing, run it again, and look at both the console and fifo.csv. If several settings change at once, it becomes hard to tell which change caused the result.

    1. Make arrivals faster than processingChange the generator's 70 ms arrival interval to 20 ms. Compare the queue length and wait time. Then restore 70 ms.
    2. Change the resource limitChange cap: 70 to cap: 50. Keep the worker count the same. Which kinds of jobs can overlap now?
    3. Change the number of workersChange both the number of spawned workers and max_workers from 3 to 1, then to 5. Watch whether the budget or the worker count is the tighter restriction.
    4. Give different jobs different durationsChange duration_ms: 300 to duration_ms: if id % 3 == 0 { 600 } else { 100 }. Watch which job IDs finish first. Sending jobs in order does not force their completion order.
    5. Inspect the states you cannot yet seeThe CSV records the waiting queue and resource reservations. It does not separately count jobs already sent into the channel or workers actually processing them. Work out where you would add those counters without changing what they mean.
    A final distinction: These examples use sleep to represent a task's duration. If you replace that with actual computation, your machine's core count and scheduling begin to matter. The value called cost will still be an artificial reservation unless you separately measure actual CPU use.

    The important question now is not simply whether the program runs. It is whether the measurements support what you claim the program is doing.
