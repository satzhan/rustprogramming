Sharing Across Timelines

A thread is a branch in the timeline. Every run of the program samples one universe from the set of possible interleavings. This is the story of who owns what while the branches are apart, told through the two questions Arc and Mutex answer.
child thread main thread
01

Two timelines

A program starts as one timeline. One instruction after another, in the order written. thread::spawn is a branch point: from that line, two timelines run apart, and nobody promises you anything about how their steps interleave. There are twenty distinct ways the six lines below can merge, and each run of the program picks one. You do not get to choose which universe you land in.

Below, main spawns one child. Both print three lines. Run it a few times and watch the universe number climb.

let child = thread::spawn(|| { for i in 1..=3 { println!("child says {i}"); } }); for i in 1..=3 { println!("main says {i}"); } child.join().unwrap();
remove join
join is where the branches converge. Main stops at that line and waits for the child timeline to catch up, and past it there is one timeline again. Flip the switch and run a few times: without join, main ends its universe whenever it pleases, and whatever the child had left to say is simply gone from it.
02

The wall

Now try to let threads see your data. Three rounds. In each one, read the code and predict the verdict before revealing it. The error messages below are the compiler's real output, not paraphrase.

Round 1: borrow it

let data = vec![10, 20, 30]; let child = thread::spawn(|| { println!("child sees {:?}", data); }); child.join().unwrap();
your call:
REJECTED
error[E0373]: closure may outlive the current function, but it borrows `data`, which is owned by the current function note: function requires argument type to outlive `'static` help: to force the closure to take ownership of `data` (and any other referenced variables), use the `move` keyword

Read the word may. The compiler is not claiming your thread will outlive main. It is saying it has no way to rule that out. A spawned thread has no known endpoint, so no borrow can be proven safe. And notice: the compiler itself hands you the next move.

Round 2: obey the hint

let data = vec![10, 20, 30]; let child = thread::spawn(move || { println!("child sees {:?}", data); }); child.join().unwrap();
your call:
COMPILES

move hands the vector to the child. No borrow, no proof needed: the child owns it now. Victory. The cost is that main gave it away, and there is only one to give. Which raises a question. What if you want three children?

Round 3: three children

let data = vec![10, 20, 30]; let mut handles = vec![]; for i in 0..3 { handles.push(thread::spawn(move || { println!("thread {i} sees {:?}", data); })); }
your call:
REJECTED
error[E0382]: use of moved value: `data` move occurs because `data` has type `Vec<i32>`, which does not implement the `Copy` trait value moved into closure here, in previous iteration of loop

This is the wall. One value. Three timelines. Ownership permits exactly one owner, and iteration one took it. The compiler's own advice walked you here, so this is not a trap someone set for you. It is the natural path, and everyone walks it.

Notice the philosophy underneath. There is no authority that steps in later to prune the universes where three branches fight over one value. Rust's answer is to refuse to branch them into existence at all.

You could clone() the vector per thread. That works, and it copies the whole house three times. The next section is about copying the deed instead.

Error text captured from rustc 1.75. Wording drifts between compiler versions; the verdicts do not.

03

One owner vs a headcount

A plain reference &T never owns anything. Somewhere, one true owner exists, and when that owner dies the data dies. So every borrow comes with a proof, checked before the program runs, that the owner outlives it. Visiting a friend's house, after the city has verified your friend will not demolish it while you are inside.

Rc abolishes the one true owner. Every clone is an equal co-owner, and the data is freed when the last one drops. Which clone drops last can depend on things that only happen at runtime, so the compile-time proof is impossible in principle. The counter is its replacement: a live headcount, standing in for a proof that can no longer be written.

let a = Rc::new(vec![10, 20, 30]); let b = a.clone(); // copies a pointer, bumps a counter. The vector is not copied.
🏠
count: 1
Deeds, not houses. Cloning hands out another deed and ticks the counter. Dropping shreds a deed and ticks it down. The last shredded deed demolishes the house. Nobody needed to prove anything in advance; the count decides at runtime.

Now the letter A. Two threads can shred their deeds at the same instant. The counter itself is shared mutable state, so decrementing it is a read, a subtract, and a write. Watch what happens when two threads do that unprotected, versus with the atomic decrement you already know.

🏠
count: 2
The A in Arc is the headcount itself. Arc's counter is maintained with the atomic fetch-and-subtract, indivisible in hardware. That one guarantee is what makes handing deeds across threads safe. This is why Rc refuses to cross a thread boundary at all: the compiler will not let a plain counter anywhere near two timelines.
04

The invisible join

Back at the wall, you might object: but I do join every thread at the end. True. And it changes nothing, because the compiler does not read your intentions. It reads signatures. Nothing in spawn's contract obliges you to join, so your discipline is a promise written in invisible ink.

Same code, two APIs. Flip between them.

let data = vec![10, 20, 30]; let mut handles = vec![]; for i in 0..3 { handles.push(thread::spawn(|| { println!("thread {i} sees {:?}", &data); })); } for h in handles { h.join().unwrap(); } // right there. every one of them.
REJECTED

The joins are three lines away and the compiler does not care. spawn demands data that lives forever, unconditionally, because you could forget to join, return early, or drop the handle. Since the language cannot prove the merge will happen, it assumes the thread lives forever.

thread::scope(|s| { let data = &data; for i in 0..3 { s.spawn(move || { println!("thread {i} sees {:?}", data); }); } }); // scope does not return until every thread inside has joined println!("main still owns {:?}", data); // and it does. nothing was moved.
COMPILES

scope is not smarter. It is structured differently: the function itself refuses to return until all its threads have joined. The merge stopped being your habit and became the API's contract. With the endpoint provable again, plain borrows flow into threads, three of them, no Arc in sight.

why the line: let data = &data;

Inside a scope, move still means move. Writing &data inside a move closure does not borrow from outside; the closure captures the vector first, then you reference your own captured copy, and the loop hits the same moved-value wall as Round 3.

Shadowing with a reference first means the closure now moves a reference. Moving a reference is a copy, so all three threads get one. The rule underneath: move captures whatever the body names, as that name is currently typed.

So which do you reach for? References work with threads whose end is provable. Arc is for threads whose end is not. That sentence is the whole decision.
05

The door, not the guard

Arc answers who owns it. It says nothing about who may touch it right now. That is a different question, so it gets a different tool, nested inside: Arc<Mutex<T>>. Read it inside out: a value, behind a locked door, whose address every branch of the timeline shares.

Keep three objects separate. The Mutex is the door, at a fixed address, alive as long as the data. The guard is the experience of currently being inside: born at lock(), alive for a few lines, and its death is what unlocks the door. The Arc is many threads holding the same address. You share the door. Nobody shares a guard. Each thread manufactures its own at the threshold, every time.

let total = Arc::new(Mutex::new(0)); // inside each thread: { let mut guard = total.lock().unwrap(); // born: door locks *guard += partial; } // guard dies here: door unlocks. The brace is the unlock.

The unlock is invisible in the source. No unlock call, just a closing brace. That makes the guard's scope a design decision, and here is what the decision costs. Two threads, one door:

thread B
A holds the guard across a sleep
The critical section is a bathroom key. Take it, do your business, return it. Do not take it to lunch. Everything A does while holding the guard, B spends waiting at the door, so keep the span down to the touch itself.
06

Freeze, then share

One pattern to keep. When many threads need to read the same structure, do not reach for locks. Build it on one timeline, freeze it, hand out deeds, and let every result travel home through the join handle.

PANEL 1

Build

main: [table ▌▌▌...] one timeline, no threads yet

Construct the structure sequentially. No coordination, because there is nobody to coordinate with.

PANEL 2

Freeze

Arc::new(table) 🔒 nobody writes from here on

Wrap it in Arc. From this line forward the structure is read-only by construction, not by promise.

PANEL 3

Share

deed → thread 1 deed → thread 2 deed → thread 3 all read at once

Clone a deed per thread. Many readers, zero locks, zero waiting. This is Arc's honest day job.

PANEL 4

Gather

h1.join() → part h2.join() → part h3.join() → part main sums parts

Each thread returns its piece through its handle. No shared accumulator needed; the merge point carries the value.

Traps worth naming

some phases are sequential

Sorting must see the whole list. Chunk after phases like that, never before. Parallelism applies per phase, not to programs wholesale.

small inputs break chunk math

8 workers, 6 items: worker 7 asks for slice [7..6] and panics at runtime. Compiles clean, detonates on small data. Skip or clamp empty chunks.

pick your integer width

Sums grow past what any single element suggests. i64 is cheap insurance; a silent i32 overflow is not.

measure before believing

Spawning threads costs real time. On small inputs the sequential version often wins. Whether it does here is an empirical question: time both, believe the clock.

do not parallelize the build

A table built by many writers behind a lock is slower and harder than a table built once and frozen. Build, freeze, share. In that order.
